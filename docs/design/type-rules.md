# Type rules

These rules decide which types exist, where each rule lives, and what the published schema may contain. The pipeline's gates check every rule marked **Gate**.

## 1. One model, three outputs

The model is built from the specification and the reviewed mapping. Everything published is derived from the model, and no output carries another output's concerns.

| Output | Holds | Used by |
|---|---|---|
| JSON Schema | The structure and constraints of one payload, plus its descriptions | Any validator and any code generator |
| Rules | Everything a schema can't check for one payload. Each rule has an ID, prose, and test vectors | Every SDK, through the conformance suite |
| Classes | Typed SDK code, generated from the model | Developers |

## 2. What the schema contains

The schema validates and explains one payload. Nothing else.

- **Standard JSON Schema 2020-12 keywords only.** They are the validation and applicator keywords, plus `title`, `description`, `examples`, and `default`. **Gate:** any `x-` key, any custom keyword, `$vocabulary`, `discriminator`, `$dynamicRef`, or `$dynamicAnchor` fails.
- **Patterns are ECMA-262 regular expressions,** as JSON Schema 2020-12 requires (core § 6.4). Python's `$` also matches before a final newline, so a Python validator that runs a pattern with `re.search` accepts `USD\n` where the standard rejects it. The conformance vectors include a trailing-newline mutant of each valid vector, and every SDK must reject it. **Gate:** every pattern gets the same verdict on every vector in ECMA-262, RE2, and Python `re` with the final `$` written `\Z`.
- **A keyword belongs in the schema only if someone who receives the payload needs it to validate or understand that payload.** Build provenance, codegen hints, class names, and package names live in the model.
- **Things the schema doesn't carry:**
  - **Mutability markers.** A marker is a rule about two versions of a payload and the party that changed it, so it belongs to the rules (§ 9).
  - **Receiver policies.** A policy, such as § 5.1's skip rule for a `channel` the receiver doesn't recognize, is receiver behavior, which also belongs to the rules.
  - **Open-vocabulary markers.** The structure already shows whether a vocabulary is open (§ 6).

## 3. Layers

Types build bottom-up. A layer uses only the layers below it. **Gate:** a reference to a higher layer, or a cycle, fails.

| Layer | Holds | Examples |
|---|---|---|
| 1. Primitives | Every scalar that validates differently from the others, or that a receiver processes differently, including a closed list that a standard fixes and no module owns (§ 3a) | `Uuid`, `ExternalId`, `Url`, `Domain`, `CurrencyCode`, `Amount`, `PercentChange`, `Fraction`, `Count`, `Measure`, `Timestamp`, `Duration`, `TimeOfDay`, `DayName`, `TimeZone`, `Digest`, `CatalogRef` |
| 2. Constructors | Parameterized forms, which exist only in the model, the parts their copies share (§ 7), and the kernel's value objects | `List<T>`, `Map<K, V>`, `Selectable<T, K>`, `Settable<T>`, `Range<T>`, `CatalogRefOr<T>`; `PriceDelta`, `CatalogReference`; `DaypartWindow` |
| 3. Vocabularies | Every value list a module owns | `Channel`, `CostMethod`, `HoldState` |
| 4. Objects | Each module's object types | `Commitment`, `HoldStatus`, `PricingEntry` |
| 5. Documents | The roots, which name the properties | `Proposal`, `LineItem`, and with the open PRs the § 2.3 `Manifest` |

Primitives form the kernel, with the vocabularies no module owns: `Marker`, the § 3 markers, and `Party`, the two parties every marker names, whose entry stays in the file of the module that owns its section and names the kernel as its module. **Gate:** a type entry that names the kernel as its module, `module: kernel`, in a file of another module cites a decision with a sentence that says the type, written as code, is the kernel's and why ("so", "because", or "since"), as D-013 says of `Party`. Modules hold the other vocabularies and the objects, and depend only on the kernel and on the modules they declare. A module declares them in its mapping file's `depends`; the kernel needs no listing, and the kernel depends on no module. **Gate:** every reference from a module's type to another module's type goes to the kernel or to a module that `depends` lists, every listed module is referenced on some lock, and the declared module graph is a DAG.

The layer of a reference is the layer of the type the emitted schema names. A copy of a constructor (§ 7) sits at the layer of the highest type it holds, and never below layer 2: `FormatsSelection`, a `Selectable` of format IDs, holds primitives, so it is in layer 2, and `AudiencesSelection` holds an object, so it is in layer 4. Its template stays in layer 2. A copy belongs to the module that states it, and a copy named after its argument, such as `AudiencesOptionOrCatalogRef`, to its argument's module. A union sits with the objects, in layer 4. A profile is a document, in layer 5.

A module owns specification sections: the line-item modules map one to one to § 5.2 through § 5.10, `proposal` to § 4, and `kernel` to § 2.2 and § 3 to § 3.2, whose types the kernel files define. § 3.3 belongs to `line-item`, with § 5 and § 5.1: its re-computation statements are about line-item fields such as `addressable_scale`, not about kernel types. Every element of a section is mapped in its module's file. **Gate:** every section belongs to exactly one module.

A profile, such as the § 2.1 Summary Representation, is a document restricted to the paths the specification lists for it. The model projects it from the document, so its fields are defined once. It projects paths, not whole fields: a path through an object, a list, or a copy of a constructor, such as `formats.included[]` or `pricing.cost_method`, makes a named object, `<profile><type>`, such as `LineItemSummaryPricingEntry`, with only the members the paths name, plus a sibling the domain model makes one of them require, as a rate requires its `currency` (§ 3a). A path listed under a requiring statement, such as § 2.1's "It MUST contain, per line item:" and the "plus" that continues it, is required at every step (§ 4). A path a decision reads from an item the list writes in prose, such as "property names", names no member, so each step keeps its object's presence, and a conditional one is optional, since the condition binds the document and the profile can't check it alone (D-028). Such a reading widens the profile by the members it names, so the mapping ties it to the prose item it reads, and it starts at a field none of the list's paths names. **Gate:** a reading of an item the list doesn't write in prose, or of a path that starts at a field a listed path names, fails. **Gate:** each path the list names is in the profile, required where a requiring statement introduces the list. An object that carries a profile, such as a § 2.3 manifest entry, which carries a proposal's summary, `includes` it and lists only the members the profile lacks. **Gate:** such a member isn't a field of the profile, and a member that is a field of the profile's document has that field's type and presence. With no `allOf` (§ 8), the object's schema carries the profile's fields itself, so the layer and module gates follow the types those fields reference, not the profile.

## 3a. Value domains

The domain model, [`kernel/domains.yaml`](../../kernel/domains.yaml), lists the value domains the specification talks about: identity, reference, text, network, money, ratio, quantity, time, term, and flag. Under each domain it lists the concepts, each with what a value means, the one type that represents it, and the specification elements and standards it rests on. It is written and reviewed before the mapping, and every type choice below follows from it. **Gate:** the file validates against its schema, and every concept's sources are current on each lock.

- **A concept gets a type of its own only when it validates differently or is processed differently.** Its values pass or fail a different constraint, or a receiver does something different with them: compares them by exact equality, compares them as instants or numbers, adds them, resolves them against the specification, fetches them, or shows them and never compares them. Where a value comes from, the party that mints it, the registry or list that defines it, or the publisher that writes it, changes neither, so it goes in the field's description, not in a type of its own: a geo code, a device category, a content category, an option's name, and a terms document's version are each an `ExternalId`, and the description names the list. A format ID is a `FormatId`, since the specification states its form, "registry format ids namespaced by channel", written `display/300x250`, so it validates differently: `300x250` isn't one (D-019). A code of a list that another standard keeps is a vocabulary that cites the list (§ 6), not a primitive. **Gate:** two kernel types with one structure fail unless a shared structure says how a receiver processes them differently (below).
- **Every kernel type represents one concept.** Each primitive and part declares its concept, and the concept names it as its type, or as one of its components, a type that exists only inside the concept's type, such as a daypart window's `TimeOfDay`. One type represents one concept, and one concept has one type. **Gate.**
- **Two types with one structure are distinct only where the domain model declares it.** An `ExternalId` and a `Text` are both strings, but a receiver compares one and never shows it, and shows the other and never compares it. The domain file lists such concepts together under `shared_structures`, each set with the decisions that make them distinct types and the reason a receiver treats them differently. Two kernel types of different concepts with one structure pass the duplication gate (§ 5) only when one set lists both concepts; two types of one concept with one structure are twins. **Gate:** an undeclared pair fails, a set whose types no longer share one structure fails, and a set that names a concept no kernel type represents fails.
- **A row a concept cites has the concept's type.** A String, Number, Integer, or Array[String] field, or a key row with no value list or inline object, that exactly one concept cites is typed by mapping rule `domain-row`, so no decision types it. A member of an inline object takes its type from the decision that types the object, and its concept from that type.
- **Every scalar property resolves to a concept**: through its type, a primitive's or part's concept, the boolean's flag, or, for a vocabulary, the vocabulary itself, since the term domain holds every vocabulary; a list or a map resolves through its items. No property is typed by a component, or by the term grammar: a property whose values are terms references a named vocabulary (§ 6). **Gate.**
- **A recurring member name resolves to one concept,** such as every `currency` to the currency concept, or the domain file lists it as a homonym with the decision that explains the difference, such as `basis`, which four objects name with four vocabularies (D-013). A listed homonym whose properties resolve to one concept fails. **Gate.**
- **Every published kernel type is used and sourced.** A primitive or part is published on a lock only where a document reaches it, and it cites a specification element in scope on that lock or a standard; a primitive that only some locks use lists them under `locks`. **Gate.**
- **A sibling a concept requires is co-present.** A concept may require a sibling member: money requires its `currency` (D-036), and every concept of a domain whose values require a sibling requires it, except the sibling's own concept. Every object that carries a money value carries a `currency` beside it, and a currency is never inherited from an enclosing object. The model derives the keywords: where the money member is required, `currency` is required; where it is optional, `dependentRequired` makes each money member present require `currency`; where the specification gives `currency` a condition, as the commitment does for `basis = spend`, the condition stands. Where the specification gives an object money and no currency, the concept's `requires` lists the element under `lacking`, and the decision covers it. **Gate:** every object that carries a value of such a concept has the sibling member, of the sibling's concept, or one of the value's elements is listed under `lacking`; every listed element is covered by the decision, and is one that a value without its sibling rests on. The gate checks that the sibling is there; the money vectors test the keywords the model derives.
- **A basis says what a sibling's value is.** The domain file lists under `bases` a vocabulary whose term says which concept a sibling member's value is: the commitment's and a `min_commitment[]` threshold's `basis` makes the `amount` money for `spend` and a count for `units` (D-036). The member keeps the type of its own term's concept and takes each other term's type while the vocabulary holds that term, which the schema states as a condition (§ 8). A basis may instead give `others`, the concept of every term it doesn't list, an open vocabulary's extension terms included: a committed metric's `metric` makes its `value` a fraction for the rates `viewable_rate` and `completion_rate`, and a measure, never negative, for any other metric, such as audience impressions for DOOH (D-005); the member then keeps the others' type, and each listed term narrows it. The money's sibling is then required only while the basis says money, and an optional basis is required with the member. **Gate:** the member's type is one term's concept's type, or the others' concept's where the basis gives one; every listed term is a term of the vocabulary; and a listed basis that no object reads fails.

The domain rules settle these choices:

| Domain | Rule |
|---|---|
| Money | A money value is a bare number of at least 0, `Amount`, a rate included, in the currency of its sibling `currency`; the one signed case, an option's price change, is `PriceAdjustment` (D-036). |
| Time | A point in time is a `Timestamp` (D-001), a flight's start and end included (D-042); a span is a `Duration`, whatever the example writes, a report's cadence and an availability's granularity included (D-040); a daypart window is a `DaypartWindow` `{ days[], start, end }` with `TimeOfDay` ends, `HH:MM` from `00:00` to `24:00` (D-004 on `main`; the text with the open PRs); a frequency cap's period is a term of `FrequencyCapPeriod`, the OpenDirect 2.1 intervals, not a span: `hour`, `day`, `week`, and `month` are calendar periods, and `flight` runs between the flight's start and end (D-044); the line item's clock reads the daypart and the period, and it is a `TimeZone`, an IANA zone name or `viewer_local`, which the open PRs add as `time_zone`; on `main` the text has no clock, and neither text names the clock of a flight's dates (D-038). |
| Identity | An ID a party mints is a `Uuid` (D-037); an ID another system keeps, or one the text calls opaque and seller-internal, such as `proposal_template_id`, is an `ExternalId`, and so is a code another list defines, such as a geo code, a device category, and a content category, whose field's description names the list (D-019), and a field of the specification that a negotiation step names by its path, for which the text states no grammar (D-027); a format ID, which the text namespaces by channel, `<channel>/<format>`, is a `FormatId` (D-019); a code of a list another standard keeps that the text names is a vocabulary that cites it, such as `ApiFramework` (D-024). |
| Version | No version is a type of its own. A proposal's `version` counts its revisions, a `Count`, and every reference to it repeats it; the specification's version, `spec_version`, and a published document's version, such as a terms document's, name a release of a document another party publishes, an `ExternalId`, carried as written, such as `3.0` and `2026.1`. |
| Term | A field whose values are terms has a named vocabulary, with no core terms where the specification lists none (D-041). D-041 lists each such vocabulary with its field. |
| Flag | A two-valued flag is a JSON boolean (D-039). |

## 4. Named or inline

A type gets a name, and every use references it, when any of these holds:

1. **It constrains a value** with a `pattern`, `format`, range, `enum`, `const`, or length.
2. **It is an object.** Every object becomes a class in every SDK, so the model chooses its name, not a generator.
3. **It is a value list.**
4. **It occurs more than once.**
5. **The specification names it,** as a subsection or a key table.

Only two forms may be inline:

- a `boolean`;
- a list or map whose items are named types, such as a list of `ExternalId`.

**Gate:** any other inline form fails.

This sets the depth of extraction. Every type is either named, or a container of named types one level deep.

- **Presence is what the specification states.** A field or key is required where the specification says REQUIRED, conditional where it says "REQUIRED when", "REQUIRED for", or "REQUIRED with" the members it names, "either" naming the two the sentence before names, and optional otherwise, RECOMMENDED included. Most fields state no presence (`presence_unstated` in the extraction report), so most are optional; the mapping doesn't guess. A member of an object is optional unless an element that a decision record covers requires it by name: a key or field row of that name whose presence isn't optional, or a MUST, SHALL, or REQUIRED statement that names the member or introduces the list that does, the list right after it or one a following "plus" continues it with. So a profile's "MUST contain" list makes each path it lists required (§ 3). A statement about the object as a whole, such as "`list_ref` MUST be hash-pinned", is a rule (§ 9), not a required member. One member is required with no such element: the `id` that the selectable template gives each object option (§ 7). The mapping keeps the presence the text gives it, optional where a property or an audience option writes `id` with none, and the model makes it required, marked as given by the constructor, whose `carries` names the decisions it rests on: D-046 for every object option, and D-047 too where the option's members are listed without it. **Gate:** in the mapping, every property has its row's stated presence, and every required or conditional member has such an element; in the model, a required member with no such element is one a constructor gives, which the model-resolves gate holds to its parameter's `carries`: typed by the parameter's argument, required, and citing its decisions.
- **An object is closed** unless the mapping marks it `open`: it rejects members it doesn't name. The specification declares no extension point, so no object has a member that carries extensions; an open vocabulary takes namespaced terms instead (§ 6). An object whose structure the specification never states is a named open object, so its members stay undefined rather than invented (D-016).
- **An object's members are the IR's.** An inline object's type lists exactly the members the specification writes, and a member written with `[]` is a list. The mapping types members and can't add one; only a constructor gives an object option the `id` that names it (§ 7). A member of an object that the mapping declares, of a profile, or of a type whose element isn't an inline object is written by its own element or by an element that a decision it cites covers: in a code span, as an inline object's key, in an identifier list, or as a key in a code block. Where no element writes a member, the object is open and leaves the member out (D-016). **Gate.**

A constraint that belongs to one member of one part stays inside that part, as a condition on the part (§ 8), and isn't a concept or a named type of its own. A daypart window's `start` is a `TimeOfDay`, like its `end`, and the window states that `start` is never `24:00`, so there is one time of day, not a start time and an end time; and the window states that its `days` hold at least one day, each once, so there is no list type of days. The pieces of an `HH:MM` value, its hour and its minute, aren't types either: rule 1 names a value, not each part of its spelling.

## 5. One rule, one place

- **Constraints live only on named types.** A property never adds a constraint beside its `$ref`, and the only keyword allowed there is `description`. **Gate.**
- **When two uses need different constraints, they are two named types,** for example `Amount` (not negative) and `PriceAdjustment`.
- **No duplicates.** The duplication gate compares the normalized structure of every named type, including every copy of a constructor (§ 7). Two names with the same structure fail, unless they represent different concepts of the domain model that a shared structure declares together (§ 3a), as `ExternalId` and `Text` do. The gate runs on the resolved model too, over vocabularies, objects, unions, documents, and profiles. A type whose structure the specification never states has no structure to define twice, so the gate sets it aside: an open object with no members but the `id` a constructor gives it as an option (§ 4, § 7, D-016), and an open vocabulary with no core terms that a decision lists with its field (§ 6, D-041). **Gate:** the value-list gate sets aside the same vocabularies, and both gates fail on an open vocabulary with no core terms that no decision lists, and on a listing whose vocabulary is gone, has terms, or isn't its field's.
- **Copies of one application are one definition.** When two fields apply the same constructor to the same arguments, such as `Settable<ExternalId>` on `geo` and `device`, their copies have the same structure. They aren't twins: the template defines them once, so they can't drift apart, and each keeps the name its field gives it (§ 7). A copy is still compared with every other named type, and with copies of other applications. **Gate.**
- **Each value list is defined once,** in the module that owns it. Every other use references it. **Gate:** two enums with the same values fail, and so does an inline copy of a list.
- **A cross-field rule belongs to the smallest object that contains every field it mentions.** It lives there once, in the schema if JSON Schema can express it (§ 8), and in the rules otherwise (§ 9).

## 6. Vocabularies

- **A closed vocabulary** is an `enum`. Examples are a state machine's states and a protocol switch.
- **An open vocabulary** is `anyOf` with exactly two branches: the core `enum`, and the kernel's `NamespacedTerm`, which is `<domain>:<term>`, where the domain is the definer's identity domain. An open vocabulary whose core terms the specification doesn't list yet is `NamespacedTerm` alone, so it accepts extension terms only (D-041); a closed vocabulary always lists its terms.
- **Which vocabularies are open** is recorded in the mapping, with a decision record for each.
- **A declared vocabulary's terms are the specification's.** Where no value list states the terms, each one is written in its own element or in an element that a decision it cites covers, such as the § 5.5 sentence "`enforcement` is `pre_serve` or `best_effort` per type". **Gate.**
- **Or another standard's code list.** A vocabulary may take its terms from a code list another standard keeps, which [`kernel/lists.yaml`](../../kernel/lists.yaml) holds as the standard writes it at a pinned commit: one term for each code, spelled as the code, or as the specification spells its terms with the code it stands for, as `flight` stands for OpenDirect's `LineDuration`. The list is named by an element the vocabulary rests on, or a decision it cites gives the list as evidence, and the vocabulary's schema names the list. Such a vocabulary is closed, unless its list reserves codes for vendors, as AdCOM 1.0's List: API Frameworks reserves 500 and up: then it is open, and its second branch is `VendorCode`, an integer of at least 500, not `NamespacedTerm`, since the list's codes are integers. So `plcmt`, `playmethod[]`, and `api[]` are the vocabularies `PlcmtSubtype`, `PlaybackMethod`, and `ApiFramework`, each the codes of its AdCOM list. Two vocabularies of two lists whose codes are the same numbers are two lists (§ 5). **Gate:** a term that stands for no code, two terms for one code, a code with no term, and a vocabulary whose openness isn't its list's each fail.
- **Terms keep the specification's spelling exactly.** A code-system value carries its name in the description, for example "Connected TV (3)". A term written as a decimal integer, such as an AdCOM code, is a JSON integer, as in AdCOM, OpenRTB, and the examples. A two-valued flag isn't a vocabulary: the `0` | `1` of § 5.2.2 is a JSON boolean (D-039).
- **A vocabulary is named for what its values are,** in the singular, qualified by its object where the field's name is generic or shared: `Channel`, `ProposalStatus`, `HoldState` (D-013).

## 7. Constructors

- **A constructor is a template in the model.** [`kernel/constructors.yaml`](../../kernel/constructors.yaml) defines each one once and cites the specification rows it comes from: `Selectable<T, K>` from § 3.1, `Settable<T>` from § 3.2, `CatalogRefOr<T>` from § 2.2, `Range<T>` from the `{ min, max }` pairs, and `List<T>` and `Map<K, V>` from `[]` and the `{ option_id: … }` form. **Gate:** every constructor cites a current row on every lock. Every constructor is applied on some lock, by a mapping entry or inside the shell of a constructor that is, as `Map` is inside `Selectable`'s `pricing`, or its `kept` cites a decision that says why it stays: a template no field uses is a form the specification doesn't write.
- **A shell is the schema of one copy.** It uses JSON Schema 2020-12 keywords, and each type position is a slot that holds a model type: a named type, a parameter, or another constructor applied to its arguments. A slot carries nothing but an optional description (§ 5).
- **The emitter publishes one concrete, named schema per use,** such as `FormatsSelection` for `Selectable<FormatId, FormatId>` on `formats`. The parts that don't depend on a parameter are named types that every copy references: `PriceDelta` and `CatalogReference`. Only the shell repeats. An option is named by its own identity in `included[]` and the `pricing` keys, and the template's `K` is the type that names it: a string option by its value, so `K` is `T`, as `Selectable<FormatId, FormatId>` names a format by its format ID; an object option by its `id`, so `K` is `Uuid`, the identity the seller mints for it (D-007, D-037). The shell's description says so. **Gate:** each use gives `K` as `T` for an option whose values are strings, a string primitive or a vocabulary, and as `Uuid` for any other option.
- **An object option carries its `id`.** Where `K` isn't `T`, each object type that is an option, directly or as the inline branch of a `CatalogRefOr` option, carries `id`, typed `K` and required, since `included[]` and the `pricing` keys name the option by it (D-046). The constructor gives the member, as its parameter's `carries` says, so the mapping keeps the members the text writes; an `id` the text writes, as a property option's, keeps its row and becomes required, and the round trip records where the rendered row gains an `id`. Where the text lists an option's members without an `id`, a closed object such as a measurement source, giving it one changes what the text settles, so the option cites the departure `carries` names too (D-047); an open option, whose members the text doesn't state, cites the gap alone. An option given as a `catalog_ref` has no `id` (D-007). **Gate:** an option that types its `id` as anything but `K` fails.
- **Every copy is generated, never hand-edited.** **Gate:** every copy equals its template applied to its arguments.
- **A constructor is never nested inside itself,** in its arguments or in the shells it expands to, such as `Selectable<List<ExternalId>>`, whose `available` would be a list of lists. A named type ends the expansion: every copy is its own schema, so a list inside an object inside a list is two expressions, not a nesting. **Gate:** in every template and every type the mapping states: a property's, a member's, and a union branch's.
- **List and map are emitted inline,** as `{ "type": "array", "items": { "$ref": … } }` and `{ "type": "object", "propertyNames": …, "additionalProperties": … }`, because they carry no rule of their own. Their items are named types or named copies (§ 4).
- **A parameter states what it accepts:** any property type, a named type, a type whose values are strings (a map key), an ordered primitive (a range bound: a number or a date-time), a named type that isn't an ordered primitive, or a closed type: one whose values aren't objects, or are objects that reject the members they don't name. **Gate:** every argument fits.
- **§ 3.2 has two forms, chosen by the value's type.** Its bounds are "either `allowed[]` (an enumerated set) or `min` / `max` (a numeric or date range)", so only an ordered type has a range: a number or a date-time, a date's range being a range of points in time (D-001). `Settable<T>` takes any named type that isn't ordered, such as a geo code or a daypart window, and has `allowed[]` only. No settable field states its bounds as the `min` / `max` form at the field: `geo`, `device`, and `daypart` declare `allowed[]`; `frequency_cap` carries its range in its `max` member, `{ min, max }`, which is `Range<T>`; `commitment` is the object of § 5.6.1, whose envelope is `commitment_bounds`, an object of four named bounds (D-021). So the model has no template that allows either form; one comes with the first field the specification bounds that way. A range gives one bound or both, and `min` is at most `max` (D-011).
- **`CatalogRefOr<T>` takes a closed type.** § 2.2 says a field carries "either an inline value or a `catalog_ref`, never both". The union holds that only when no value of `T` can also carry `catalog_ref`, so `T` is closed. A strict validator can't state "never both" beside the union for every `T`, because the condition applies only to objects and `T` may be a string. An object the mapping defines is closed unless it is marked `open` (§ 4), and the gate fails for an open object, or for a type whose closedness the model doesn't record.
- **Names follow from the specification.** A copy of `Selectable`, `Settable`, or `Range` is named after its field in PascalCase: `<Field>Selection`, `<Field>Bounds`, `<Field>Range`. A field name is written as it is, with no singular form, so `formats` gives `FormatsSelection`. The field is the one the mapping entry's IR element names. A field or key row names the last segment of its path, so `pricing[].floor` gives `Floor`. A member of an inline object has the ID `<object ID>/<member path>`, the form the IR gives a member's value list, and is named after its key whether or not it has a row of its own: `max` in `frequency_cap`'s object, `field:5.5:frequency_cap#description/object:1/max`, gives `MaxRange`. An element that names no single field, such as the inline object itself or the `valid_from, valid_until` row, gets its name from the mapping, with a decision record. A copy of `CatalogRefOr` can stand where no field names it, as an option in `available[]`, so it is named after its argument: `<T>OrCatalogRef`. An array field's item is `<Field>Entry`, so `negotiation_history[]` becomes `NegotiationHistoryEntry`. The mapping may override a name only with a decision record. Objects follow the same scheme, by the field or member that holds them: an object field's value is `<Field>`, such as `Commitment`, an array field's item is `<Field>Entry`, an option in `available[]` or `allowed[]` is `<Field>Option`, such as `PropertiesOption` and `DaypartOption`, and a key table describes the object of the field it names. **Gate:** every copy's name matches `^[A-Z][A-Za-z0-9]*$`, two different copies can't get one name, and a copy can't take the name of a type the model defines. Every object the mapping defines has the name its holder gives it, unless a decision it cites writes its name as code.
- **The § 3.1 and § 3.2 fallbacks are a parameter.** The specification doesn't say what a bare value is (D-008), so `Selectable` and `Settable` take its type as the optional `B`. A use that supplies it gets `anyOf` the bare value and the full form, named `<Field>SelectionOrValue` or `<Field>BoundsOrValue` (§ 8). Without it, the copy is the full form only. No use supplies it in draft 1 (D-018).
- **A rule a shell can't express is a constructor rule,** with an ID `constructor:<Constructor>:<token>`, a source, and vectors, as § 9 requires. Every copy carries it.

## 8. Unions and conditions

| Keyword | Allowed for |
|---|---|
| `oneOf` | Tagged unions only. Every branch has a required property with a `const` value that names the branch. **Gate** |
| `anyOf` | Open vocabularies (§ 6), and the untagged unions draft 1 requires (below) |
| `if` / `then` / `else` | Conditional requirements, for example "`currency` REQUIRED when `basis` is `spend`", and a member's type while a sibling holds a term, such as `amount`, a `Count` when `basis` is `units` (§ 3a). The conditions of one object read one sibling, each value once, and chain through `else`, so none needs `allOf` |
| `if` / `then: false` | A value one member of a part can't take, such as a daypart window's `start` of `24:00`: `if: { type: object, properties: { start: { const: "24:00" } }, required: [start] }, then: false`. The `if` names `object`, so a value of another JSON type fails only on `type` |
| `dependentRequired` | A member that another member's presence requires, such as the `currency` beside each optional money member of a price entry (§ 3a), and with the open PRs the `time_zone` a `daypart` requires ("REQUIRED with either") |
| `dependentSchemas` | A condition that holds when a member is present, such as § 3.2's "either `allowed[]` or `min` / `max`", written `dependentSchemas: { allowed: { maxProperties: 1 } }`. It means the same as an `if` that requires the member, which Ajv's strict mode rejects (`strictRequired`), so the gates can validate every copy strictly. It also states a member required with a member of a sibling's object, as `time_zone` is with `frequency_cap.period`: `dependentSchemas: { frequency_cap: { if: { properties: { frequency_cap: { type: object, required: [period] } } }, then: { required: [time_zone] } } }`, which sits beside the object's own `if` / `then` with no `allOf`. |
| `allOf` | Not used. Objects are named and referenced whole, so no schema inherits from another. **Gate** |

Draft 1 requires these untagged unions:

- the § 3.1 and § 3.2 fallbacks, where a bare value stands in for the full form, though no field takes one yet (D-018);
- the § 2.2 choice between an inline value and a `catalog_ref`;
- a type written with a slash (D-017): `materials_due`, whose "Timestamp/Offset" forms are told apart only by string format, and `specifications`, whose String/Object forms are told apart by JSON type;
- with the open PRs, `geo`, which § 5.5 lets declare either the selectable structure or `allowed[]`, never both (D-022).

The schema expresses each of them with `anyOf`, and each one also goes in the implementation feedback as a place where the specification should add a tag.

## 9. Rules beyond the schema

Some rules can't be expressed in JSON Schema, for example:

- one field compared with another, such as `end` later than `start`, or `min` at most `max`;
- membership across fields, such as each `included[]` entry naming an option in `available[]`;
- uniqueness by a key;
- arithmetic, such as `derived_units`;
- mutability: which party may change which field, in which state, between two versions;
- receiver behavior, such as skipping an unknown `channel`.

Each such rule gets:

- an ID;
- the specification text it comes from;
- the object that owns it (§ 5), or the kernel's `Marker` vocabulary for a rule about every field that carries a marker;
- what it applies to: its owner; the owner's property, as `Proposal.negotiation_history`, when the statement sits in that property's field or key row, which is then one of its sources; every property that carries the marker; or every copy of the constructor;
- at least one valid and one invalid test vector. A mutability rule's vector is a pair of versions plus the acting party.

The conformance suite publishes the vectors, and every SDK must pass them. **Gate:** a rule without vectors fails.

- **An invalid vector of a SHOULD-level rule is a warning.** RFC 2119 lets an implementation depart from a SHOULD, SHOULD NOT, RECOMMENDED, or NOT RECOMMENDED with a reason, so such a vector is reported, not rejected. An invalid vector of any other rule, a MAY rule's included, is an error: a MAY grants only the change it names (D-034), and the vector shows a change beyond it. Each rule states which, as its `severity`, from its level.
- **A constructor rule is listed on every lock,** even where no copy uses the constructor and its `applies_to` is empty, because a language with generics generates the template itself (§ 10), and the rule holds there.

- **IDs come from the text.** A rule that the mapping states takes its IR element's ID, such as `rule:5.5:2eab2842`. A marker's rule takes its § 3 row's ID, such as `marker:3:seller-set`, and holds the statements in that row, such as "The seller sets it and MAY revise it while status is `draft` or `published`", so the marker is one rule. A primitive's or a constructor's rule keeps its kernel ID (§ 7).
- **A vector has one of three forms.** A payload, for a rule about one payload. A pair of versions, `before` and `after`, plus the `party` that made the change, for a mutability rule; every marker rule's vectors are pairs. A payload plus the `response` its receiver makes, `process`, `skip`, or `reject`, for receiver behavior. A vector may add `context`: a fact the rule reads that the payload doesn't hold, keyed by the property that holds it elsewhere, such as `Proposal.seller_id`.
- **The schema accepts every vector.** Each payload of a valid or an invalid vector is an instance of the schema of the vector's type, so the rule alone decides it. **Gate.**
- **A condition the schema can't state is a rule.** A conditional property that `if` / `then` can't express (§ 8) is stated by a rule, whose vectors entry lists the condition's row under `sources`, so the row is one of that rule's sources. A rule that only mentions the property doesn't count. **Gate.**
- **Vectors are reviewed input.** They live in `vectors/<module>.yaml`, one entry per rule, in the file of the module that owns the rule's section. An entry stores its rule's element digest, so it goes stale when the rule's text changes, and cites a decision record where its vectors read more than the sentence says (D-034, D-035). An element beyond the rule's own text that a vector rests on, such as "`converted` is terminal" for the hold transitions, goes under the entry's `sources`; the cited decision covers each one, and each joins the rule's sources. **Gate.**

A requirement that no payload can show is an **obligation**, not a rule: what a party does, such as a seller rejecting a stale commitment attempt, or an inspecting implementation not firing an event URL. Each obligation names its party (`seller`, `buyer`, `consumer`, or `implementation`) and goes to the obligations list, with no schema keyword and no vector. Most MUST sentences outside the tables are obligations (`must_without_field` in the extraction report).

## 10. Classes

The emitters generate classes from the model, not from the schema. Names are stable, and a language that has generics gets them, as in `Selectable[FormatId, FormatId]`. A plain generator run on the published schema alone must still produce correct concrete classes. The conformance vectors hold both to the same verdicts. **Gate:** datamodel-code-generator, at the version `tools/plaingen/requirements.txt` hash-locks, runs with stock options on each published schema file; where it can't express a constraint the schema states, each case it gets wrong is a numbered exemption with the reason, and a listed case that it gets right fails the gate.

## 11. Mapping

The mapping (stage 3) says what each IR element becomes: a property, a named type, a term, a rule, an obligation, a profile, an example, a statement a named type's schema already expresses, informative text, or rendered output.

- **Every IR element is mapped exactly once on each lock,** in the file of the module that owns its section. An element that differs between the locks gets one entry per lock. **Gate.**
- **A row's location follows from its path.** A field row is a property of its document, a sub-field row such as `pricing[].floor` of `PricingEntry`, and a key row of the object its table names. **Gate.**
- **Deterministic rules come first.** A mapping rule ([`src/mapping-rules.ts`](../../src/mapping-rules.ts)) maps what the IR, the domain model, and these type rules decide, such as a row a concept cites to the concept's type (§ 3a) or an Appendix A row to rendered output, and `npm run map` writes its entries. An entry that cites a rule is what the first rule that applies derives. **Gate.**
- **Every other entry cites one or more decision records,** and each record quotes and digests the entry's element, so a change to the element makes both stale. A decision covers only what no rule decides: an entry that cites a decision where a rule applies fails. **Gate.**
- **A decision is a gap or a departure,** as its record's `kind` says. A gap chooses a reading where the text leaves a point open. A departure proposes a change to what the text settles, or to the form its examples write, such as a UUID where the examples write readable names (D-037). The implementation feedback lists the two apart.
- **The schema says what the text states, or a departure says why not.** The fidelity gate reads from the IR alone each constraint in a form that needs no judgment, a REQUIRED or OPTIONAL row, a conditional REQUIRED, a value list (in a cell, an inline object, a sentence "`x` is `a` or `b`", or a named list's codes), a MUST-contain list, an inline object's members, "MAY be empty", a stated type, and a YAML example the text writes, and checks a valid and an invalid vector of each against the emitted schema. A disagreement fails unless a departure covers that exact element and lists the constraint's form under that cover's `departs`, so a departure about an element's type doesn't excuse a change to its presence, and a departure about one element excuses nothing on another it covers. A form a cover lists that excuses no disagreement fails too. A MUST-contain list is a projection: each object one of its paths steps into, below the profile itself, holds only the members the list's paths name there and a sibling the domain model makes one of them require (§ 3a), so a summary that carries a whole field where the list names one of its paths fails. So is a list of the paths a summary gives "whichever of" its record declares, each step optional, and a path a decision reads from a list's prose item joins that list's projection, as "property names" joins § 2.1's, only when it starts at a field none of the list's code paths names, since a reading into an object a listed path projects would widen what that object may hold. No rule excuses a disagreement by naming the element among its sources, so a domain rule or a constructor rule never silently overrides a more specific statement: a constraint the schema can't state, such as a condition on a member outside the object, passes only when `gates/fidelity-expected.yaml` lists it with its rule, the rule applies to an object on the constraint's path, and one of the rule's invalid vectors is a payload the constraint rules out. **Gate.**
- **A decision digests every element it rests on,** not only the entries that cite it. The IR records each prose sentence that names an identifier as a `sentence` element, even with no RFC 2119 keyword, so a decision that rests on such a sentence, or on a code block, covers it. A sentence maps to informative text by rule; the decisions that cover it carry its meaning.
- **Every type the mapping names is defined once,** as a primitive, a constructor, a part, a type entry, a declaration in a mapping file's `types`, or a profile, and every reference has the kind it needs. **Gate.**
- **Examples are checked against the model, not read into it.** A sentence that names a file under `examples/`, in a section whose title names one document, maps to an example of that document by rule, and a code block maps to one by a decision. Every example loads under YAML 1.2 core with JSON types only, validates against its document's schema, uses only keys the model defines, an open object's included, and keeps every rule that one payload decides: each such rule has a deterministic check, [`src/rule-checks.ts`](../../src/rule-checks.ts), that gives each of its vectors its verdict, and the check runs on every value of the type the rule reads, a code block's fields as part of their document. A rule about two versions or about what a receiver does has no check on one example, and neither has a rule that rests on a list this repository doesn't pin, as ISO 4217's currency codes and the IANA zone names. A check that turns on what an example leaves out, such as the proposal's seller for a line item alone, leaves it undecided. **Gate:** a rule that one payload decides has a check or rests on an unpinned list, and each check gives every vector of its rule its verdict. Where it doesn't, the failure is a recorded finding that cites the decisions its location rests on, one per cause, and goes to the implementation feedback; the model doesn't change to fit an example. A finding whose cause is a departure says that the example follows the text and what we propose: its reason opens "The example follows the text", says "We propose", and uses no wording that blames the example. **Gate.**

## 12. Proposed, not in the specification

The schema is derived from the specification, so it has no type the specification doesn't state. Two designs from the [initial conventions](initial-conventions.md) (§ 7 and § 8) are our proposal for the working group, not generated schema. The specification states neither, and the IR of both locks has no element that names an extension or `conforms_to`, so the model has neither and the emitter publishes neither.

- **The extension envelope.** The kernel would define `ExtensionEntry` once: `{ uri, digest, must_understand?, data }`, with `data` opaque to the core. A module would declare where an extension may attach, as an `extensions` list it owns, each with the policy `always`, `flag`, or `never`. The policy is receiver behavior, so it would be a rule (§ 9), not a schema keyword (§ 2). The [initial design](initial-design.md) proposes a policy for each host.
- **The conformance declaration.** A document would declare once, at its root, `conforms_to: { release, digest, extensions[] }`, and a line item that is a document root would carry it too. It isn't named `version`, which § 4.1 already uses for the proposal's revision counter.

What would make either one generated is the specification stating it. Its fields then enter the IR, the mapping maps them like any other element, and the emitter publishes them. Until then, the SDKs' extension registry, which keys a validator by an extension's URI and digest, has no generated type that calls it.
