# OpenProposal schema tooling

Tooling that produces the machine-readable schemas for IAB Tech Lab's OpenProposal 3.0 from its markdown specification, and the registry of AdCOM 1.0's code lists, which OpenProposal and other standards cite, from AdCOM's (see [AdCOM](#adcom)). Nobody writes a schema by hand. Every schema, rule, and SDK type is a function of the specification text plus a reviewed mapping, so the specification and the schemas can't drift apart.

## Method

1. **Extract.** A deterministic parser reads a pinned revision of the specification, upstream `main` by default or `main` with the open PRs applied, and writes an intermediate representation (IR). The IR holds every field, type, marker, enum, inline object form, RFC 2119 statement, and prose sentence that names an identifier. No model calls.
2. **Map.** A reviewed domain model lists the value domains and concepts the specification talks about, each with the one kernel type that represents it. A reviewed mapping file then assigns each IR item to a type, a module, and a schema location. Deterministic rules cover what they can. An agent proposes an entry only where the prose is ambiguous. Each agent entry has a decision record that quotes the specification rows it covers, and the record goes stale when those rows change.
3. **Generate.** Deterministic emitters turn the mapped model into concrete (monomorphized) JSON Schema 2020-12, built up from kernel primitives, plus SDK types, the specification's own tables, and the documentation. A rule JSON Schema can't express stays in prose with a rule ID, and ships with test vectors that every SDK must pass.
4. **Check.** Gates cover:
   - Coverage: every IR item is mapped exactly once.
   - Duplication: each primitive and each list is defined once.
   - Conventions: union rules, layering, and modules.
   - Drift: the generated output equals the committed output.
   - Round trip: the rendered tables equal the markdown.
   - Validity: the examples validate.
   - Breaking changes: compared against the last release.
5. **Repeat until clean.** The decision records together are the implementation feedback for the working group, which `npm run feedback` renders (see [Implementation feedback](#implementation-feedback)).

The model plays the role a compiled descriptor plays in a protobuf toolchain. There is one source, and every artifact is regenerated from it and diffed byte for byte.

## Decisions

- **Language:** TypeScript (Node 22) for the whole pipeline. Python and Go bindings are generated outputs, not tooling. The gates also run Python 3.12 and Go, but only to cross-check verdicts: the reference oracle (python-jsonschema) and the RE2 regular expression engine.
- **Schema language:** JSON Schema 2020-12 only. No protobuf and no CEL. A rule beyond JSON Schema is prose plus published test vectors.
- **Input:** upstream `main` at one pinned commit, by default. The open-PR integration build is a second, optional lock.
- **Layout:** each specification has its own folder under `specs/`. OpenProposal's locks, IR, mapping, decision records, vectors, and every output generated from them sit under [`specs/openproposal/`](specs/openproposal/), and the paths this page names for them, such as `schemas/` or `feedback/comment.md`, are relative to that folder. The tooling (`src/`, `gates/`, `scripts/`, `tools/`), the kernel (`kernel/`), the format schemas of the records (such as `mapping/mapping.schema.json`), the gate decisions (`gates/decisions/`), and the SDK trees (`sdk/`) stay at the repository's root.
- **Spec profile and plugin:** each spec folder's [`spec.yaml`](specs/openproposal/spec.yaml), valid against [`specs/spec.schema.json`](specs/spec.schema.json), names the specification, says whether the pipeline reads its text or imports a published schema set, lists the documents its field rows describe, and turns on the features it uses: markers, appendices, and profiles. A specification read from its text names a plugin under `src/specs/<plugin>/`, whose readers ([`src/specs/plugin.ts`](src/specs/plugin.ts)) give its table layouts and row readers, its type and presence grammar, its value-list forms, its section numbering, and its RFC 2119 policy, and optionally its rule checks, its fidelity readers, and its round-trip notation. The extractor reads everything else the same way for every specification. OpenProposal's plugin is [`src/specs/openproposal/`](src/specs/openproposal/).
- **Names:** the profile's `names` give what the outputs carry: the specification's name in prose, the base of every schema's `$id` (`https://openproposal.noetis.dev/` for now), and the SDK packages (the Python package, its receive-mode key and entry-point group, the Go module and package, and the npm package). Its `site` gives what the spec's pages on the site name: the type the type map opens at, the field How it's built follows, and each lock's label; and its `feedback` gives the feedback's issue, supporting page, our pull requests, groups, rows, and suggestion. [`specs/site.yaml`](specs/site.yaml) gives the site itself. The emitters read every name from it, so a second spec's outputs carry its own.
- **Kernel binding:** the kernel files, `kernel/primitives.yaml`, `constructors.yaml`, and `domains.yaml`, hold only what is true of a type in every spec: its definition, constraints, vectors, showcase values, and the standards and design sections it rests on. Each spec's [`kernel-binding.yaml`](specs/openproposal/kernel-binding.yaml) ([`src/binding.ts`](src/binding.ts)), valid against [`kernel/binding.schema.json`](kernel/binding.schema.json), mirrors them and gives what rests on that spec's text: the elements each type cites, the decisions it follows and on which locks, the locks it exists on, and the member names the spec uses, such as the `currency` an amount requires beside it. The loaders merge the two into one kernel per spec, and the kernel gates run on each spec's. A kernel file that holds a spec's key, or a binding that gives a definition, fails the load.

## Usage

Requires Node 22. The gates also need Python 3.12 and Go 1.25 or later.

```sh
npm ci --ignore-scripts
npm run setup:oracle             # create .venv with the hash-locked reference oracle (tools/oracle/requirements.txt)
npm run fetch                    # materialize the default lock into build/spec/ and verify the blob SHA
npm run fetch -- --lock <lock> --snapshot   # rewrite the lock's snapshot under spec-input/snapshots/ from its clone
npm run extract                  # stages 1 and 2 for the default lock, written to ir/
npm run extract -- --lock specs/openproposal/spec-input/with-open-prs.lock.yaml   # written to ir/with-open-prs/
npm run cite -- '<IR element ID>' # print an element's digest and quote for a mapping entry or decision record
npm run cite -- --all-locks '<ID>'  # the same, scoped to each lock where the element differs
npm run map                      # write the rule entries and the canonical layout of mapping/*.yaml
npm run resolve                  # stage 4: build/model.json per lock, then the convention gates
npm run emit                     # stage 5a: the JSON Schema 2020-12 files under schemas/, per lock
npm run rules                    # stage 5b: the rules and their vectors in rules/rules.json, per lock
npm run corpus                   # stage 5e: the conformance corpus in corpus/cases.json, per lock
npm run type-examples            # a minimal and a full example payload per named type, in type-examples/examples.json, per lock
npm run setup:sdk                # install the hash-locked Pydantic (tools/sdk/requirements.txt) into .venv, for the Python SDK's gate
npm run setup:plaingen           # install the hash-locked datamodel-code-generator (tools/plaingen/requirements.txt) into .venv, for the plain-generator gate
npm run sdk                      # stage 5c: the TypeScript, Python, and Go types, as written under sdk/ and ours under sdk/proposed/
npm run emit -- --variant as-written   # one variant only, here the as-written one; --variant proposed for ours
npm run render                   # stage 5d: the spec's tables rendered from the model, compared with the spec
npm run examples                 # gate 10: the spec's examples validated against the schemas, compared with examples/findings.yaml
npm run release                  # stage 7: schemas/release.json per lock, compared with the last frozen release
npm run compare                  # the comparison of each lock with the default lock, in comparison/
npm run feedback                 # the implementation feedback for the working group, in feedback/
npm run fidelity                 # the fidelity gate: the schemas against what the IR states, report in build/fidelity.json
npm run gates                    # the gates whose fingerprint no gate decision accepts, as a record's accepts list
npm run provenance               # the line provenance of a lock that merges open PRs, from its clone, in spec-input/provenance/
npm run site                     # the public site, in site/
npm run site:deploy              # print the rsync command that copies site/ to the server; it runs nothing (deploy only after an export)
npm run release -- --freeze      # also keep the manifest, model, rules, and schemas as releases/<lock>/<version>/
npm test                         # unit tests and golden snapshots
npm run ci                       # every gate; the same script runs in GitHub Actions
```

A lock lists its sources in order: a local clone, given relative to the spec's folder, such as `../../vendor/OpenProposal`, then the lock's snapshot, then a raw URL. A maintainer's clone goes under the root's `vendor/`, which git ignores. The snapshot, `spec-input/snapshots/<lock>/`, holds the specification and every file under `examples/` at the locked commit, at their paths. The lock pins each file's blob SHA and the tree SHA of `examples/` as `examples_tree`, so the snapshot is checked against the lock with no clone, and CI, which has no clone, runs every gate from it. A lock that merges PRs names, in `heads_on`, the day each head in `merge_order` was its PR's live head, and lists in `edits` what the integration changed outside the PRs beside resolving their conflicts; the feedback's inputs quote both. After a lock changes, rewrite its snapshot with `npm run fetch -- --lock <lock> --snapshot`. With no source reachable, an optional lock (`required: false`) is checked from its committed IR files instead. After an intended change to the extractor, run `UPDATE_GOLDEN=1 npm test` and review the diff under `test/golden/`.

## Mapping and decision records

- **Mapping.** `mapping/<module>.yaml` holds the entries for one module, names the specification sections the module owns, and lists in `depends` the other modules its types may reference. Each entry names one IR element, stores its digest, says what decided it (a mapping rule, or one or more decision records), and says what the element becomes: a property with a type and a presence, a named type (with its members, for an object), more members of a declared object, a restated type, a vocabulary term, a rule, an obligation on a party, a statement a named type's schema already expresses, an example, a profile of a document, informative text, or rendered output. A type is a named type, the inline boolean, a constructor applied to a type, or a constructor's parameter. A file's `types` declares the types that no single element defines: the documents, the objects that key tables and sub-field rows describe, and the open objects, unions, and vocabularies that a decision gives. An open object's declaration gives a `description`, what its row says of it, since it names no members, and the schema and the SDK types carry it. A vocabulary no module owns names the kernel as its `module`, as `Party`, the two parties every § 3 marker names, does beside `Marker`; its entry stays in the file of the module that owns its section.
- **Rules first.** A mapping rule maps what the IR, the domain model, and the type rules decide, such as an Enum field to its value list's vocabulary, a row that a concept of the domain model cites to the concept's type (`domain-row`), or an Appendix A row to rendered output. `npm run map` writes every rule entry and rule type, and keeps every entry and type that cites a decision, and each file's `depends`, as it is. A rule entry must be what the first rule that applies derives, and an entry can't cite a decision where a rule applies.
- **Decisions.** `decisions/D-<nnn>.yaml` holds one decision. It states the question, quotes and digests each IR element it rests on, and lists the options, the chosen one, the rationale, and the feedback for the working group. A mapping entry or type that cites a decision must be one of the elements the decision covers. A departure lists under `departs` the constraint forms it changes, such as `values` for the `0` | `1` flags that become booleans (D-039); the [fidelity gate](#fidelity) lets the schema disagree with a covered element only in a listed form.
- **Bijection.** On each lock, every IR element has exactly one entry, in the file of the module that owns its section, and every entry names a current element. A field or key row is a property of the object its path names, with the presence the specification states: required only where it says REQUIRED. An inline object's members are exactly the IR's, and a member written with `[]` is a list. Every type the mapping names is defined once. The mapping files are what `npm run map` writes. These are the gates `npm run ci` runs per lock, with the checks in [`src/coverage.ts`](src/coverage.ts).
- **Sources.** What the mapping adds rests on cited text. Every member of a declared object or a profile, and every declared vocabulary term, is written by its own element or by an element that a cited decision covers. A member is required only where such an element states REQUIRED, MUST, or SHALL for it by name. An object that includes a profile doesn't restate the profile's fields. Every object the mapping defines is named after the field or member that holds it, or a cited decision names it. The checks are in [`src/mapping-sources.ts`](src/mapping-sources.ts).
- **Staleness.** A table row's digest is the extractor's digest of its source bytes. Any other element's digest is the SHA-256 of its canonical JSON without its location, so moving it doesn't make it stale. When an element changes, every entry and record that stores its digest fails the gate until someone reviews it and runs `npm run cite` again.
- **Locks.** An entry or a cover applies to every lock unless it lists `locks`. An element that differs between the locks needs one entry per lock.

## Value domains

- **The concept inventory.** [`kernel/domains.yaml`](kernel/domains.yaml) is the logical model the mapping rests on (type rules § 3a). It lists 10 value domains, identity, reference, text, network, money, ratio, quantity, time, term, and flag, and under each its concepts. A concept has a type of its own only where its values validate differently or a receiver processes them differently; where a value comes from goes in the field's description (type rules § 3a). A concept states what a value means, names the one model type that represents it, a kernel primitive or part or the boolean, and cites the specification elements and standards it rests on. A field or key row a concept cites is typed by that concept's type, by mapping rule `domain-row`, so no decision types it.
- **Kernel types declare their concept.** Every primitive and part names its concept, which names it back as its type or as a component, a type that exists only inside the concept's type, such as a daypart window's `TimeOfDay`. One concept has one type. Two kernel types with the same structure are distinct only where the domain file lists their concepts together under `shared_structures`, with the decisions that make them distinct types and the reason a receiver treats them differently, as it does for `ExternalId` and `Text`.
- **The domain rules.** A money value is a bare number, `Amount`, in the currency of the `currency` beside it in the same object, never an enclosing object's; where the money member is required the currency is required, and where it is optional `dependentRequired` makes it required with the money (D-036). A basis says what an amount is: a commitment's or a `min_commitment[]` threshold's `amount` is money, with its currency required, when `basis` is `spend`, and a count of units, with no currency, when `basis` is `units`. An option's price change is the signed `PriceAdjustment`. A point in time is a `Timestamp`, a flight's start and end included (D-042), a span is a `Duration`, a report's cadence and an availability's granularity included (D-040), and a daypart window is a `DaypartWindow` `{ days[], start, end }` with `TimeOfDay` ends, `HH:MM` from `00:00` to `24:00`, where only `end` can be `24:00` (D-004 on `main`; the text with the open PRs). A frequency cap's `period` is no span but a term of `FrequencyCapPeriod`: the OpenDirect 2.1 `Line.frequencyinterval` intervals `hour`, `day`, `week`, and `month`, calendar periods read on the line item's clock, with weeks from Monday, and `flight`, OpenDirect's `LineDuration`, which runs between the flight's start and end, on both locks (D-044). A daypart window and a calendar period are read on the line item's clock. With the open PRs, that clock is `time_zone`, a `TimeZone`: an IANA zone name or `viewer_local`, required with a `daypart` (`dependentRequired`) or a `frequency_cap.period` (`dependentSchemas`). On `main` the text has no clock, and the feedback asks for the one the open PRs add; neither text says which clock reads a flight's dates (D-038). An ID a party mints is a `Uuid`, and an ID, a code, or a version another system or list defines, or one the text calls opaque and seller-internal such as `proposal_template_id`, an `ExternalId`: a format ID, a geo code, a device category, a content category, an option's name, and a terms document's version included, each with a description that names its source, since a type exists only where a value validates or is processed differently (type rules § 3a). A code of a list another standard keeps is a vocabulary that cites the list, such as `ApiFramework`, `PlaybackMethod`, and `PlcmtSubtype` (D-024), and a geo bound and a device bound are copies of one application, `Settable<ExternalId>`. A field whose values are terms has a named vocabulary, with no core terms where the specification lists none, and D-041 lists each such vocabulary with its field. A flag is a boolean (D-039).
- **Gates.** `npm run ci` checks:
  - the file: every concept's type and components declare it, every primitive and part declares a concept that names it, every decision a concept, a homonym, a shared structure, or a basis cites exists, every concept of the money domain but the currency requires a currency, and every element a concept lists as lacking its sibling is covered by the decision that asks for it;
  - sources, on each lock: every concept's spec sources are current, and a concept whose type the lock publishes cites an element in scope or a standard;
  - use, on each lock: every primitive and part the lock publishes is reached from a document and cites an element in scope or a standard, so a primitive no payload can hold, such as `Uri` was, isn't published; `Digest`, `TimeZone`, and `VendorCode` list the locks they are published on;
  - properties, on each lock: every scalar property resolves to a concept, none is typed by the term grammar or by a component, and every object that carries money carries a currency, or one of the money's elements is listed as lacking one, and every listed element still lacks one; a basis is read where its vocabulary is;
  - homonyms, across the locks: a member name that recurs with two concepts, such as `basis` or `version`, is listed with the decision that explains the difference, and a listed one that no longer differs fails.

## Kernel primitives

- **One definition each.** [`kernel/primitives.yaml`](kernel/primitives.yaml) defines the 21 primitives of type rules § 3. Each one has a JSON type, the concept it represents, one constraint set written with standard 2020-12 keywords, a description, and its sources: quoted and digested spec elements, external standards, and design sections. A constraint the sources don't state cites a decision record. A primitive only some locks use lists them under `locks`.
- **Vectors.** Each primitive lists values it must accept and reject. The conformance vectors add a trailing-newline mutant of each valid vector of a primitive with a `pattern`, `format`, or `enum`, which must be rejected. The gate checks every vector with Ajv 2020 in strict mode, with `format` asserted, and with the reference oracle, python-jsonschema as [`tools/oracle/requirements.txt`](tools/oracle/requirements.txt) pins it, with its format checkers installed. A rule that JSON Schema can't express, such as "an assigned ISO 4217 code", has an ID (`kernel:<Primitive>:<token>`), a source (spec elements, a standard, or a decision record), and vectors that the schema accepts.
- **Showcase values.** Each primitive also declares one or two `showcase` values, which a reader's example payload shows where the specification's examples give none (see [Type examples](#type-examples)), such as a realistic UUID or an amount of 18.5; the second is for a list's second item. The kernel gate checks each one with the Ajv validator that checks a valid vector, and against each rule of the primitive, so a showcase currency is one ISO 4217 assigns. They aren't conformance vectors.
- **Patterns.** A pattern is an ECMA-262 regular expression, as JSON Schema 2020-12 requires. It can't use lookaround, backreferences, named groups, inline flags, or `\d`, `\w`, `\s`, `\b`, and `\p`, which ECMA-262, RE2, and Python read differently. The gate also runs every pattern on every string vector in ECMA-262, Go's RE2 ([`tools/regexcheck`](tools/regexcheck)), and Python `re`, and fails on any verdict that differs.
- **Trailing newline.** Python's `$` also matches before a final newline, so `re.search("^[A-Z]{3}$", "USD\n")` matches, and python-jsonschema 4.26.0 accepts `USD\n` as a `CurrencyCode`. Its `date-time` and `uri` format checkers do the same. JSON Schema 2020-12 and the RFC grammars reject these values, so the mutants stay invalid, and every SDK validator must reject them. The gate runs Python `re` with the final `$` written `\Z`, which must agree with ECMA-262 everywhere. It counts the mutants that unanchored Python and the stock oracle accept, and fails on any other difference, except a vector [`tools/oracle/gaps.yaml`](tools/oracle/gaps.yaml) lists with the verdict the oracle gives.
- **Oracle gaps.** The oracle's `date-time` checker, rfc3339-validator 0.1.4, rejects two values RFC 3339 § 5.6 allows: the leap second `2016-12-31T23:59:60Z`, since its grammar writes the seconds as `[0-5]` and a digit, and the year `0000`. Both are Timestamp valid vectors, which Ajv and the SDKs accept, so each is a numbered gap in [`tools/oracle/gaps.yaml`](tools/oracle/gaps.yaml), validated by its schema, with the reason. The gate fails on a disagreement the file doesn't list, on a listed one that no longer occurs, and on a file written for other versions than the pins.
- **Code lists.** [`kernel/lists.yaml`](kernel/lists.yaml), validated by [`kernel/lists.schema.json`](kernel/lists.schema.json), holds the code lists other standards keep that the specification cites, each with its codes and labels as the standard writes them at a pinned commit, such as OpenDirect 2.1 `Line.frequencyinterval`, or, for a list its keeper publishes outside git, at the `version` the keeper gives it, with the URL and the SHA-256 of the file: ISO 4217 List One at its 2026-09-17 publication, and the zone and link names of the IANA time zone database release 2026e. SIX serves List One at a URL that names no version, so the repository keeps the file it served, [`kernel/sources/iso-4217-list-one-2026-09-17.xml`](kernel/sources/iso-4217-list-one-2026-09-17.xml), and the kernel gate checks that its SHA-256 is the pinned one, that it was published on the pinned date, and that it holds exactly the list's codes and labels; a list whose URL names no version and that has no copy fails. The currency-code and zone-name rules read those two lists, so they run over the examples like every other rule one payload decides. A vocabulary that cites a list holds one term for each code, spelled as the code or mapped to it, as `flight` stands for `LineDuration` in `FrequencyCapPeriod` (type rules § 6), and the sources gate checks it against the list in place of the elements that write terms.
- **Duplication gate.** Every named type is defined once, and a mapping entry can't define a type with a primitive's name. Two named types with the same normalized structure fail, unless they are kernel types of different concepts that the domain file lists together under `shared_structures`, as it lists `ExternalId` and `Text`; two kernel types of one concept with one structure fail, and so does a set whose types no longer share a structure. The structure ignores annotations and enum order.

## Constructors

- **Templates, not schemas.** [`kernel/constructors.yaml`](kernel/constructors.yaml) defines `Selectable`, `Settable`, `Range`, `CatalogRefOr`, `List`, and `Map` (type rules § 7), each applied on some lock, the two parts their copies share, `PriceDelta` and `CatalogReference`, and the kernel's value object, `DaypartWindow`, which a part's slots build from primitives, other parts, and lists of them. A part may also reject one value of one member with `if` / `then: false`, as `DaypartWindow` rejects a `start` of `24:00`; such a constraint stays in the part (type rules § 4). A primitive's `decision` and a rule's apply only on the locks `decision_locks` lists, where the sources state the constraint on the others, and a part lists its `decisions`, one for each member or constraint the sources don't state, each with the `locks` it applies on: `DaypartWindow` cites D-004 for its shape and its `start` that is never `24:00`, and D-038 for its clock, on `main` only, and D-045 for its `days`, which hold at least one day, each once, on both locks. A part may also bound one of its own lists, with `minItems` and `uniqueItems` on the list's slot, as a daypart window's `days` holds at least one day, each once: the list is filled in place, so the bounds sit on the list itself, and the constraint stays in the part (type rules § 4). Each part declares its concept, and a part's rule, such as `kernel:DaypartWindow:ordered`, has vectors the part's schema accepts. Each one cites its spec rows, quoted and digested. A shell is the schema of one copy, with a slot, `$model`, at each type position. A mapping entry applies a constructor with `{ kind: apply, constructor, arguments: { T: … } }`.
- **Copies.** The emitter makes one named copy per use, named after the field or object member its mapping entry names: `FormatsSelection` for `Selectable<FormatId, FormatId>` on `formats`, whose second argument, `K`, names an option in `included[]` and the `pricing` keys: the option's own type for a string option, and `Uuid`, the option's `id`, for an object option, which the gate checks (D-007), `GeoBounds` and `DeviceBounds` for `Settable<ExternalId>`, `DaypartBounds` for `Settable<DaypartWindow>`, `MaxRange` for `max` in `frequency_cap`'s object, and `AudienceOrCatalogRef`, named after its argument. Copies of one application on two fields have the same structure; they aren't duplicates, because the template defines them once. `List` and `Map` are filled in place. When a use supplies the bare-value type `B` (D-008), the copy is `anyOf` the bare value and the full form, such as `FormatsSelectionOrValue`.
- **Members a constructor gives.** A parameter that names another's options, as `Selectable`'s `K` names `T`'s in `included[]` and the `pricing` keys, says under `carries` the member each object option carries for it: `id`, typed by `K` and required, with the decisions it rests on, `decision` for every object option (D-046) and `departure` for a closed option whose members the text lists without it (D-047). The model gives the member to each object type that is an option, directly or as the inline branch of a `CatalogRefOr`, marks it given by the constructor, and cites the decisions on the option, so the mapping keeps the members the specification writes. An option that types the member as anything but `K` fails, and so does an option that isn't an object.
- **Vectors and rules.** Each constructor lists copies to build, with values each must accept and reject, and the gate checks them with Ajv 2020 asserting `format`. A rule a shell can't express, such as `constructor:Range:ordered` or `constructor:Selectable:options-named` (D-007), has vectors that the schema accepts.
- **Nesting gate.** No constructor occurs inside an application of itself, in its arguments or in the shells it expands to. The gate runs on every template and on every type the mapping states, a property's, a member's, or a union branch's, so `Selectable<List<ExternalId>>`, whose `available` would be a list of lists, fails. A named type ends the expansion.

## Model and conventions

- **The model.** `npm run resolve` combines one lock's IR, the mapping, the decision records, the primitives, and the constructors into `model.json`, the one input every emitter reads. It is canonical JSON: every map is keyed by name and every list is sorted, so the order of the mapping files and entries doesn't change a byte. The default lock's model is `build/model.json`, and another lock's is under `build/` at its IR directory, such as `build/with-open-prs/model.json`.
- **What it holds.** Every named type once, with its kind, its layer (type rules § 3), its module, the IR elements and decisions it rests on, and the named types its emitted schema references. Primitives and parts carry their schemas, and constructors their templates. Every copy the mapping's applications make is applied, with its filled shell. A vocabulary lists its terms in specification order, a decimal term as a JSON integer. An object, a document, or a profile lists its properties with their type, presence, condition, marker, and description; a profile takes its fields from its document, and a member it projects is described by what it holds of the document's field, such as "The line item's `formats`, projected to `included[]`." A field row's marker is its Mutability cell. A key table has no Mutability column, so a key row that writes a marker in its Required cell, as `derived_units` writes `derived`, gives its property that marker (§ 3: every field carries one). The rules, obligations, schema statements, and examples are listed with their text.
- **Resolution fails** on a name defined twice, a property of no object, a term of no vocabulary, a restated value list with a value its vocabulary lacks, a profile field its document lacks, and a copy named after its field that two modules state.
- **Conventions.** On each lock's model, `npm run ci` checks:
  - layers: no type references a higher layer, and no reference chain is a cycle;
  - modules: a reference to another module's type goes to a module the mapping file lists in `depends`; across locks, every listed module is used and the declared module graph is a DAG;
  - named or inline: every property, union branch, and slot is a named type, the boolean, a named copy, or a list or map of named types or named copies;
  - nothing beside a reference: a `$ref` or a slot carries a description at most, and a property only its type, presence, and annotations;
  - keywords: every schema and shell the model holds uses standard JSON Schema 2020-12 keywords only;
  - unions: no `allOf`, `oneOf` only with a `const` tag in every branch, `anyOf` only at the root of a union copy, and every union cites a decision;
  - lists: no two vocabularies, or a vocabulary and a kernel list such as `DayName`, have the same values, and no `enum` outside a primitive;
  - duplication: the duplication gate over every named type in the model, which sets aside the open objects whose structure the specification never states (D-016) and the open vocabularies with no core terms that D-041 lists with their fields; an unlisted one, or a stale listing, fails;
  - value domains: see [Value domains](#value-domains).
- **Determinism.** The gate runs `npm run resolve` twice in separate processes and compares both files with the in-process model, byte for byte. A test resolves the mapping with its files, entries, and declarations reversed and gets the same bytes.

## Schemas

- **One function of the model.** `npm run emit` resolves each lock's model and emits it with [`src/emit.ts`](src/emit.ts), which reads nothing else. The default lock's files are under `schemas/`, and another lock's under `schemas/` at its IR directory, such as `schemas/with-open-prs/`. Every named type the model holds is emitted once, with two exceptions that exist only in the model: the constructors, which are templates, and a vocabulary that lists a model attribute's values, such as `Marker`, whose terms are the § 3 marker rows and which owns the marker rules (type rules § 2). Every copy of an application is its own concrete, named schema.
- **Files.** `kernel/1/kernel.json` holds the primitives, the parts, and any kernel vocabulary it emits, and `modules/<module>/1/<module>.json` holds a module's vocabularies, objects, unions, and copies, all under `$defs`. `documents/1/<document>.json` holds one document or profile as its root schema, so a payload validates against the file itself. The `1` is the major version, in the path and the `$id`; minor versions and digests belong to the release manifest, `release.json` at the root of the tree (see [Release](#release)). Each `$id` is the file's path under the spec's `$id` base, `https://openproposal.noetis.dev/` for OpenProposal, which the profile gives. The multi-spec site serves each file at its path under the spec's path, and the `$id`s move to those paths before the first frozen release (see [Site](#site)). Every `$ref` between files is relative, so the tree resolves the same at any base.
- **What a type becomes.** A vocabulary is an `enum`, and an open one is `anyOf` its core `enum` and `NamespacedTerm`, or `NamespacedTerm` alone while the specification lists no core terms; a code's label, such as `1`: Instream, goes in the description. An object lists its properties, `required` as the specification states it, `dependentRequired` for a money member's `currency`, and `additionalProperties: false` unless the mapping marks it open. An object that includes a profile carries the profile's fields itself. A union is `anyOf` its branches. A property is a `$ref`, the boolean, or an inline list or map, with its row's description beside it and nothing else. No mutability marker appears, neither on a property nor as a vocabulary.
- **Conditions.** A conditional property whose condition names a sibling and one of its values, such as "REQUIRED when `basis = spend`", becomes `if` / `then` on its object. Any other condition, such as `plcmt`'s "REQUIRED for video ads (`channel` `video`, …)", is a rule; the emitter lists it, and the gate reports it. Two such conditions on one object would need `allOf`, so the emitter fails instead.
- **Gates.** On each lock, `npm run ci` checks:
  - drift: two runs of `npm run emit` in separate processes write the same files as the in-process emitter, and the committed tree holds exactly those files, byte for byte;
  - output conventions: every file has its `$schema`, its `$id` at its path, a title, and a description; only standard 2020-12 keywords, so no `x-` key, `$dynamicRef`, or `discriminator`; nothing beside a `$ref` but a description; every `$ref` resolves; no `allOf`, `oneOf` only tagged, and `anyOf` only at the root of an open vocabulary, a union, or a union copy; and every required name is a property of its object;
  - Ajv: each file validates against the 2020-12 meta-schema and compiles in strict mode with every reference resolved. `strictRequired` is off, because it reads a `then`'s `required` against the `then` alone; the output gate checks required names instead;
  - the reference oracle: [`tools/oracle/schema_check.py`](tools/oracle/schema_check.py) runs python-jsonschema's 2020-12 meta-schema check on each file and resolves every `$ref` with `referencing`, both as [`tools/oracle/requirements.txt`](tools/oracle/requirements.txt) pins them.

  Across the locks, every file git tracks under `schemas/` must be one that some lock emits, so a hand-written file anywhere under `schemas/` fails.

## Rules

- **What a rule is.** A rule is a requirement on a payload that JSON Schema can't express (type rules § 9): a comparison, a membership across fields, a uniqueness by key, arithmetic, mutability between two versions, or receiver behavior. `npm run rules` resolves each lock's model, emits its schemas, and writes its rules to `rules/rules.json`, and another lock's under `rules/` at its IR directory, such as `rules/with-open-prs/rules.json`. The file is canonical JSON, and lists the rules sorted by ID.
- **Which rules.** Every mapping entry that the model lists as a rule, under its IR element's ID, such as `rule:5.5:2eab2842`. One rule per mutability marker, owned by the `Marker` vocabulary, under its § 3 row's ID, such as `marker:3:seller-set`; a rule statement in a marker row, such as "The seller sets it and MAY revise it while status is `draft` or `published`", is part of that marker's rule, so no marker is stated twice. The primitives', parts', and constructors' rules, with the vectors that `kernel/primitives.yaml` and `kernel/constructors.yaml` give them.
- **What each rule carries.** Its ID; its owner, the smallest object that holds every field it mentions (type rules § 5), `Marker`, a primitive, or a constructor; the specification text it comes from and its RFC 2119 level; its `severity`; the IR elements and decisions it rests on; what it applies to: its owner, the owner's property when the statement sits in that property's row, as `Proposal.negotiation_history` (the row is then a source), every property that carries the marker, as `LineItem.min_spend`, or every copy of the constructor; and its vectors, with the type and the schema `$id` their payloads are instances of. A constructor rule is listed on every lock, even where no copy uses the constructor and `applies_to` is empty, because a language with generics generates the template itself.
- **Severity.** An invalid vector of a rule at SHOULD, SHOULD NOT, RECOMMENDED, or NOT RECOMMENDED is a `warning`: RFC 2119 lets an implementation depart from it with a reason, so a conformance suite reports the vector and doesn't reject it. Every other rule's invalid vector is an `error`, a MAY rule's included, since a MAY grants only the change it names (D-034).
- **Vectors.** `vectors/<module>.yaml` holds one entry per rule, with at least one valid and one invalid vector. A vector is a payload; a pair of versions, `before` and `after`, with the `party` that made the change; or a payload with the `response` its receiver makes. A vector may give `context`, a fact the payload doesn't hold, keyed by the property that holds it, such as `Proposal.seller_id`. An entry stores its rule element's digest, and cites a decision where its vectors read more than the sentence says: D-034 for the mutability rules and D-035 for the rules on one line item. An element beyond the rule's own text that the vectors rest on goes under the entry's `sources`, such as "`converted` is terminal" for the hold transitions, or the `placement.plcmt` row for the rule that states its condition; the cited decision covers each one, and each joins the rule's sources.
- **Gates.** On each lock, `npm run ci` checks:
  - every rule has at least one valid and one invalid vector, so a rule without vectors fails;
  - every vector entry names a rule on the lock, stores its rule's current digest, sits in the file of the module that owns the rule's section, and cites a decision that covers the rule and every element under its `sources`; a vector type is one the schema emits; every marker rule's vector is a pair; no vector is both valid and invalid; and every context key names a property;
  - every condition the schema leaves to the rules, such as `plcmt`'s "REQUIRED for video ads", has its row listed under `sources` by the vectors entry of the rule that states it; a rule that only mentions `plcmt` doesn't count;
  - isolation: Ajv 2020, asserting `format`, accepts every payload of every vector against its type's emitted schema, and every context value against its property's type, so the rule alone decides each vector;
  - drift: two runs of `npm run rules` in separate processes write the in-process bytes, and the committed file equals them.

  Across the locks, every file git tracks under `rules/` must be one that some lock emits.

## Round trip

- **What it renders.** `npm run render` resolves each lock's model and renders the specification's tables from it with [`src/render.ts`](src/render.ts), in the notation of OpenProposal's plugin, [`src/specs/openproposal/render.ts`](src/specs/openproposal/render.ts): every field table, every key table, the § 3 marker table, the value-definition tables of § 5.1.1 and § 5.2.1, Appendix A, Appendix B, and the figures of "What the distribution says". The § 1.1 concept table is informative, so the model holds nothing of it.
- **From the model.** What the model owns is rendered from it: a field's name and its path from its document, such as `pricing[].floor`, with `[]` for a list; its Type in the specification's notation; its marker; a key's name and presence; a vocabulary's terms; and Appendix A and B whole, with their counts and the owner labels, such as `` `status` (proposal) ``. Inside a description or a meaning, each value list and each inline object the row holds is rendered from the type of the row's property: a value list as its vocabulary's terms, and an inline object as its object's members, with a member's values where its own list defines its vocabulary, and a range's `{ min, max }`. The prose around them is copied from the IR, because the model doesn't own prose.
- **Type notation.** A primitive is its JSON type (`String`, `Integer`, `Number`, `Boolean`), a `date-time` is `Timestamp`, and a `duration` is `Offset` (D-017). A flag's `0` | `1` renders as the boolean's `false` | `true` (D-039). A vocabulary is `Enum`, an object or a copy of an object constructor is `Object`, a list is `Array[…]`, and a union joins its branches with `/`, so `materials_due` is `Timestamp/Offset`.
- **Rows.** Rows keep the specification's order, and each pairs with the IR row its property, term, or appendix entry cites. A property, a term, or a field the model holds with no row of its table is a row the specification lacks, and an IR row the model doesn't hold is a row the model lacks.
- **The comparison.** Each cell is compared with the IR's after normalizing whitespace, escaped pipes, and backticks. A key's Required cell is compared as the presence it states (type rules § 4): `REQUIRED`, the condition of a conditional key, the marker that stands in the cell, or else `OPTIONAL`, `RECOMMENDED` included. The IR holds every cell's source markdown, and the extraction gates keep it equal to the pinned specification on both locks, so the round trip runs in CI even where the optional lock's clone is absent.
- **Differences.** [`roundtrip/differences.yaml`](specs/openproposal/roundtrip/differences.yaml) records each difference: its table, row, and column, the specification's and the model's text, the decision record that makes the model differ, and a reason. Each lock has one: D-024 writes the `properties` option's plural members, `domains`, `supported_formats`, and with the open PRs `apps`, as lists, which the inline object writes without `[]`. With the open PRs, D-039 also writes the `0` | `1` of `placement.reward`, `instl`, and `skip` as the boolean's `false` | `true`.
- **Gates.** On each lock, `npm run ci` checks that the renderer places every value list and inline object the IR records; that every difference is recorded with its current text and a decision that covers an element its row rests on; and that every recorded difference still occurs. Across the locks, every recorded difference names known locks.

## Examples

- **Which examples.** The model's examples. A sentence that names one file under `examples/`, in a section whose title names one document, points to an example of that document, by the `example-file` mapping rule: "See `examples/proposal.yaml`." under § 6.1 Proposal is a `Proposal`, and "See `examples/manifest.json`." under § 6.6 Publication manifest is the § 2.3 `Manifest`. A code block that a decision maps to an example (D-033), such as the § 5.5 `geo` block, is part of a line item, so each field it holds is validated against that field's schema.
- **Pinned files.** Each lock lists its example files under `examples` with their git blob SHAs, and `npm run examples` fetches them, as `npm run fetch` fetches the specification, into `build/spec/<lock>/examples/`. A raw URL source serves an example at the specification's URL with the example's path in place of the specification's. The gate fails on a file the specification names that the lock doesn't list, on a listed file it doesn't name, and on a file under `examples/` at the commit that the lock doesn't list. A clone or the snapshot lists the directory, and the listing must hash to the lock's `examples_tree`.
- **Loading.** YAML 1.2 core with unique keys, so `no` stays a string and `2026-09-24` stays a string. A value JSON can't hold fails to load: a key that isn't a string, `.inf` or `.nan`, or an unknown tag. A `.json` example loads the same way.
- **Validation.** Ajv 2020, strict, with `format` asserted, on the lock's emitted files. A failure is one location in the example: the errors under a union that matches no branch are one failure at the union, and a key a closed object doesn't name is one at the key. A key of an open object (D-016) passes the schema, but the model doesn't define it, so a walk through the schemas flags it too, following only the union branches that accept the value. The reference oracle, python-jsonschema with formats asserted ([`tools/oracle/instance_verdicts.py`](tools/oracle/instance_verdicts.py)), must reach Ajv's verdict on every example.
- **Rules.** Every rule that one payload decides has a deterministic check, in [`src/rule-checks.ts`](src/rule-checks.ts) for a kernel or constructor rule and in [`src/specs/openproposal/rule-checks.ts`](src/specs/openproposal/rule-checks.ts) for a rule of the specification, which gives each of the rule's vectors its verdict, and the gate runs it on every value of the type the rule reads: each copy of `Selectable` for its option names, each range and daypart window for its order, and each line item for the rules its object owns, a code block's fields as part of a line item. A rule about two versions or about what a receiver does has no check on one example. A rule that rests on another body's list, ISO 4217's currency codes or the IANA zone names, reads the list as [`kernel/lists.yaml`](kernel/lists.yaml) pins it. A range compares its bounds by the type its copy's `T` names, numbers as numbers and timestamps as instants, and a daypart window its times of day; a value the schema rejects compares as nothing. A check that turns on what an example leaves out is undecided: the proposal's seller for a line item alone, a member a code block leaves out while it shows another the rule reads, a vendor a `catalog_ref` option stands for, and the video ads of a `ctv` line item with no `plcmt`, which no field states (D-035). Each undecided check is recorded under `undecided` in [`examples/findings.yaml`](specs/openproposal/examples/findings.yaml) with the decision that says why, and the gate fails on one not recorded and on a recorded one that is decided now.
- **Findings.** [`examples/findings.yaml`](specs/openproposal/examples/findings.yaml) records each failure: its example, location, and kind (`load`, `invalid`, `undefined_key`, or `rule`, with the rule it breaks, and `severity: warning` for a SHOULD rule's, which the feedback counts apart from the errors), the example's value there, the decision records that the location rests on, one per cause, and a reason. Each decision covers an element of the deepest model type or property at the location, as a round-trip difference's covers its row. Each finding goes to the implementation feedback, by the kind of its causes. A finding's causes are all gaps or all departures, so it sits in one of the feedback's two tables; a place with one failure of each kind is two findings. Where every cause is a gap, the example disagrees with the text, and the reason says which side should change: the date in `materials_due`, the unstated keys of `suppression_list` and of a manifest entry, the name of an option given as a `catalog_ref` (D-007), the manifest entry's missing `linked_execution` (D-028), and the hash and URL placeholders. Where a cause is a change we propose, a departure, the example follows the text, and the reason opens "The example follows the text" and says what we propose: every readable name where a party mints an ID, which we propose as a UUID (D-037), a production option's readable `id` among them; the `id` we propose for the production, measurement source, and reporting options, whose members the text lists without one, so the display example's measurement sources and reports, named by `vendor` and `feed_type`, have none (D-047); AdCOM's `0` | `1` for a flag (D-039), `daily`, `30d`, and `10 business days` for a span (D-040), the unlisted terms such as `mrc` and `vast_4_2` (D-041), and a flight's calendar dates (D-042). The examples gate fails a departure's finding that doesn't use the template or that blames the example, and a finding that cites a gap and a departure.
- **Gates.** On each lock, `npm run ci` checks the lock's list of example files; that every example loads and validates against its document, uses only keys the model defines, and keeps every rule a check decides, or that each failure is a recorded finding with its current value and a decision that covers its location; that every recorded finding still occurs; and that the oracle agrees with Ajv. An optional lock with no reachable source is skipped. Across the locks, every finding names known locks.

## Release

- **The manifest.** `npm run release` resolves each lock's model, emits its schemas and its rules, and writes `release.json` at the root of the lock's schema tree, beside `kernel/`, `modules/`, and `documents/`, with [`src/release.ts`](src/release.ts). It lists every file by its path in the tree, with its version and its digest, and gives the digest of the tree, `{ <path>: <schema> }` over every file, of the model, and of the rules, `rules.json`. It names the lock, its pinned commit and blob, the last frozen release it is compared with as `previous`, and the changes since then.
- **Digests.** A digest is the SHA-256 of the value's RFC 8785 (JCS) bytes, written as the kernel's `Digest` writes one, 64 lowercase hex characters. It hashes the value, not the file's bytes, so a receiver recomputes it from the parsed schema with any JCS implementation, whatever the file's whitespace.
- **Versions.** A release version is `MAJOR.MINOR.PATCH`, as Semantic Versioning 2.0.0 writes it, and its major is the one in every path and `$id`. The first release is `1.0.0`. After that, the version follows from the differ's verdict against the last frozen release: an additive change, which is any other change to what a payload must satisfy, bumps the minor; a change that alters no validation, such as a description, a term's label, or the spec pin, bumps the patch; and no change keeps the frozen release, manifest and all. A file keeps its version while its digest is unchanged, and takes the new release's version when its digest changes.
- **Breaking changes.** A change is breaking where a payload valid under the last release may be invalid under this one: a removed type, property, term, or union branch; a type that moves to another file, so its `$id` changes; a narrowed type, such as a new `pattern`, a tighter bound, a property typed `Uuid` where it was `ExternalId`, or a case that narrows a property while a sibling holds a term; a new required or conditional member, or an optional one that becomes either; a changed condition; a vocabulary or object that closes; a member typed on an open object, which accepted it with any value; a changed mutability marker, which narrows what a party may change between two versions; a type whose kind changes; a profile that projects another document or lists fewer fields or paths; a new rule at `error` severity on a type or property the last release had; and a rule that now rejects what it accepted, because a vector valid under the last release is invalid, its severity rises to `error`, or it covers a type or property it didn't. A change it can't show to keep every value counts as narrowing.
- **What the differ compares.** It reads three views of each release. The models, type by type, with the schemas of primitives, parts, and copies keyword by keyword. The rules, by ID and by content: a marker's, a primitive's, and a constructor's rule keep their IDs while their statements and vectors change (type rules § 9), so a kept rule's statement, severity, sources, targets, and vectors are compared, and a change the vectors don't show to reject more is additive; a change to its owner, decisions, or standard alone is an annotation. And the emitted schema files, each file's root and each `$defs` entry, following every `$ref` across files, so a change the model doesn't show, such as one the emitter makes, is classed too. A change both the model and the files show is listed once per view. The other half of gate 12, that every valid case of the old corpus still validates, is a gate of its own (see [Corpus](#corpus)). The rules are prose with vectors, not code, so no gate can run a new rule on an old payload: a new error-level rule on an existing type stays breaking, and a kept rule whose content changes without a flipped vector stays additive.
- **Frozen releases.** `npm run release -- --freeze` keeps a lock's manifest, its model, its rules, its corpus, and its schema tree as `releases/<lock>/<version>/`, the tree under `schemas/` and the corpus as `corpus.json`. They are what the next release's differ and corpus check read. A frozen release can't change: freezing its version again with other bytes fails. A release rests on reviewed decisions only (gate 6): freezing fails while a decision the model or the rules cite is still `proposed`. The model lists every decision a mapping entry or declaration cites, under its own `decisions`, so a decision that only a property's type or an informative row rests on, such as D-015, counts too.
- **Gates.** On each lock, `npm run ci` checks that the manifest builds from the model; that two runs of `npm run release` in separate processes write the in-process bytes and the committed `release.json` equals them; that every digest recomputes byte for byte from the committed files, the model, and the rules, in TypeScript and with Python's rfc8785 as [`tools/oracle/requirements.txt`](tools/oracle/requirements.txt) pins it ([`tools/oracle/release_digests.py`](tools/oracle/release_digests.py)); that no change against the last frozen release is breaking within the major; and that every valid case of that release's corpus still validates. Across the locks, every frozen release validates, sits at its lock and version, holds the schema tree its manifest lists, and its tree's, model's, and rules' digests recompute, in both languages; no decision a frozen model or its rules cite is still `proposed`; and every file git tracks under `releases/` is the format schema or part of a frozen release.

## Corpus

- **What it holds.** `npm run corpus` resolves each lock's model, emits its schemas and its rules, and writes its conformance corpus to `corpus/cases.json`, and another lock's under `corpus/` at its IR directory, such as `corpus/with-open-prs/cases.json`, with [`src/corpus.ts`](src/corpus.ts). It is canonical JSON with three lists: the constraint cases, the implied keywords, and the rule cases, each sorted by ID. It names the oracle that labels it, the jsonschema version [`tools/oracle/requirements.txt`](tools/oracle/requirements.txt) pins.
- **Constraints.** A constraint is one validation keyword at one place in one named type's schema: a `type`, `enum`, `const`, `pattern`, `format`, bound, length, or count; each name a `required` lists, a condition's `then` included; each name a `dependentRequired` member requires, whose baseline holds the member; a `$ref` a condition's `then` gives a member, which narrows its type while the condition holds, such as `Commitment#/else/then/properties/amount/$ref`, whose mutant is a fractional count of units; an `additionalProperties: false`; and a union's `anyOf`. Constraints live only on named types (type rules § 5), so the walk stops at each `$ref` and each constraint belongs to one type. An `if` is a condition, not a constraint, so nothing under it is walked; a condition chained in `else` is walked like the first. A constraint's ID is the type and the pointer to the keyword in its schema, with the name for a `required` entry, such as `Commitment#/then/required/currency`. A keyword the corpus doesn't know fails the generator.
- **Cases.** Each constraint has a baseline and a mutant. The baseline is the smallest valid instance of the type that reaches the constraint: a primitive's first valid vector in [`kernel/primitives.yaml`](kernel/primitives.yaml), a vocabulary's first term, and for an object its required members, the member on the way to the constraint, and what `minProperties` and a condition's `then` need, with the `if` made to hold where the constraint sits in the `then`. The mutant changes the value at the constraint's instance location, `path`. It is drawn in order from a primitive's reviewed invalid vectors, then from a fixed list per keyword, such as one past a bound, a member removed or renamed, or a value of another JSON type, and the first that isolates the constraint is kept. A `pattern`, `format`, `enum`, or `const` on a string also gets the trailing-newline mutant of type rules § 2, where it isolates the constraint.
- **Isolation.** A mutant isolates its constraint when the type's schema rejects it and the same schema with that one keyword removed, or that one `required` name, accepts it. So nothing beside the constraint rejects it, and a validator that drops the constraint fails the case. A `type` beside an `enum` or a `const` whose values all have that type adds nothing the values don't state, so no mutant can isolate it; the corpus lists it as implied, with the keyword that implies it.
- **Rule cases.** Each rule's valid and invalid vectors, with its severity and the type and schema its payloads are instances of. The schema accepts every payload, so the rule alone decides each vector (type rules § 9).
- **Labels.** Ajv 2020, asserting `format`, decides each candidate while the corpus is generated. The reference oracle, python-jsonschema with formats asserted, as [`tools/oracle/requirements.txt`](tools/oracle/requirements.txt) pins it, labels the corpus: its verdict on every baseline, mutant, and rule payload must be the label. The one exception is the Python `$` defect: the stock oracle accepts a trailing-newline mutant of a `pattern`, or of a `date-time` or `uri` format, which the gate counts, and every SDK must still reject.
- **Gates.** On each lock, `npm run ci` checks:
  - the corpus generates with no problem, so every constraint has an isolating case and every rule its vectors;
  - isolation, on the committed file by itself: its cases are exactly the constraints the schemas state, each baseline is valid, each mutant is invalid and valid with its one keyword removed, every implied keyword's sibling states it, and every rule's vectors are the rule's;
  - drift: two runs of `npm run corpus` in separate processes write the in-process bytes, and the committed file equals them;
  - labels: the oracle reaches every label, except the trailing-newline mutants it counts;
  - gate 12, its second half: against the last frozen release, every baseline of its corpus validates under the new schemas, by its `$id`, and every valid vector of a rule still validates under its type's new schema, and the kept rule doesn't list it as invalid.

  Across the locks, every file git tracks under `corpus/` must be one that some lock generates.

## Type examples

- **What it holds.** `npm run type-examples` resolves each lock's model, emits its schemas, and writes, for every named type the schemas emit, a minimal and a full example payload to `type-examples/examples.json`, and another lock's under `type-examples/` at its IR directory, such as `type-examples/with-open-prs/examples.json`, with [`src/type-examples.ts`](src/type-examples.ts). Each entry names the type's kind and its schema's `$id`. The documents and the summaries have entries too; a constructor has none, since only its copies have a schema. The file is indented JSON with each object's members in its schema's order, for a reader, such as the type map's payload panel.
- **Values.** A scalar at a property takes the first value the specification's own examples give at that property, where the property's emitted schema accepts it: the lock's example files and the code blocks the model maps to an example, read from the specification's first section to its last, each value in the order its example writes it. A value the schema rejects, such as the readable ID `business-daily-display` where a UUID is required, is skipped. A member whose schema is an open object takes the whole object an example gives it, such as the display example's `suppression_list`. A member of a summary takes the values the examples give the member it projects, such as the proposal's `seller_name` for the proposal summary's. Otherwise the member takes its per-field example value, below, and else a primitive takes its showcase value (see [Kernel primitives](#kernel-primitives)), and a vocabulary its most representative term: the first term a specification example uses, such as `published`, and else its first core term. A list's second item takes the second value of the same source. `npm run type-examples` prints how many of the full examples' own values come from each source.
- **Per-field values.** [`field-examples/field-examples.yaml`](specs/openproposal/field-examples/field-examples.yaml), validated by [`field-examples/field-examples.schema.json`](field-examples/field-examples.schema.json), gives a value for a member the specification's examples give none, so a reader sees a plausible payload rather than one generic sentence or one external ID everywhere: `Net 30 from the end of the calendar month` for a line item's `payment_terms`, an `https` URL for an asset's `url_or_tag`, AdCOM device type codes for `device`, a namespaced term such as `examplepub.example:mrc` for an open vocabulary with no core terms, and ordered bounds, such as a flight that ends after it starts. Each entry names the member by the IR element its property rests on and the member's name, such as `field:5.10:billing#description/object:1` and `payment_terms`, and may be for some locks only. A value is the member's whole value; a second value is for a selection's second option. An entry may carry a note, which the type examples list under the type's `illustrative` with the value's location in the full example: the open objects' values follow the structures D-016's feedback proposes, and their notes say that the structure is our proposal, not the specification's, since the schema keeps those objects open. The values are for readers' examples only, not conformance vectors.
- **Minimal.** The type's corpus baseline (see [Corpus](#corpus)): its required members, and what `minProperties` and a condition that holds need, with each scalar the value above where the example still holds, and else the baseline's own. A primitive's is its showcase value, and a vocabulary's its representative term.
- **Full.** Every member present, one item in each list, one key in each map, the first branch of each union, and the members a condition's `then` requires or narrows where the condition holds. A list of scalars holds two items where the specification's examples give two values there. A selection holds two options: the first in `included[]`, and the second priced in `pricing`, by the first price delta the specification's examples give that field, or else the full price delta, with a `max_select` of at least 1, the specification's or else the number of options. A part whose rules read its members starts from the value every rule of the part lists as valid. Where a member's full value breaks the schema or a rule, the example keeps the member's minimal value, or leaves it out, and the entry's `notes` say which and why: a price delta holds exactly one delta, and with the open PRs, a line item's `exclusions` holds every exclusion type, which its `exclusions_accepted` doesn't list. A rule that can't decide without something a payload of the type doesn't hold is listed under `undecided`.
- **Gates.** `npm run ci` checks that the per-field example values file is valid against its schema, and on each lock that every entry in scope names a member that exists, by its IR element and name; that each value is valid against the member's emitted schema and breaks no rule, on its own and in place in its type's full example; that no value is one the specification's examples give the member, or the member it projects; that the specification's examples give the member no value, so the entry still applies; and that a value of a vocabulary with core terms is one of them. On each lock, it checks that every example builds, is valid against its schema under Ajv 2020 with `format` asserted, and breaks no rule one payload decides ([`src/rule-checks.ts`](src/rule-checks.ts)), on any value of a type the rule reads; that two runs of `npm run type-examples` in separate processes write the in-process bytes, and the committed file equals them; and that the committed file, by itself, has one entry per named type and passes the same check. Across the locks, every file git tracks under `type-examples/` must be one that some lock generates.

## SDK types

- **From the model, not the schema.** `npm run sdk` resolves each build's model and generates its types in three languages (type rules § 10). The as-written build is the default tree, since it is the closest to what a consumer of the specification writes: `sdk/` for the default lock, and `sdk/` at another lock's IR directory, such as `sdk/with-open-prs/`. The schemas we propose are an opt-in tree under `sdk/proposed/`, such as `sdk/proposed/with-open-prs/`. Each tree holds `ts/`, a TypeScript package on Zod 4; `python/`, the package `openproposal` on Pydantic 2; and `go/`, a Go module with the standard library only. [`src/sdk.ts`](src/sdk.ts) builds the language-neutral form that [`src/sdk-ts.ts`](src/sdk-ts.ts), [`src/sdk-python.ts`](src/sdk-python.ts), and [`src/sdk-go.ts`](src/sdk-go.ts) write. What a type's schema states beside its properties' types, such as what an object requires, whether it is closed, and its condition, comes from the emitter's own schema of the type, and the builder checks that each property's model type is the type the schema references, so the classes and the schema can't state two different things. A keyword the builder doesn't know fails it, so no constraint is dropped.
- **Names and generics.** Every named type the schema emits is one declaration of the same name in each language. Every constructor that the schema doesn't fill in place is a generic template, used or not, since a constructor rule holds for the template itself (type rules § 9): `Selectable<T>` in TypeScript, `Selectable[T]` in Python and Go, with `CatalogRefOr` a generic union and each fallback (D-008) a generic union such as `SelectableOrValue<T, B>`. A property typed by a copy of `Selectable` is typed by the template applied to the copy's arguments, such as `Selectable<FormatId, FormatId>` for `formats`, and the copy `FormatsSelection` is an alias of that application. `List` and `Map` become each language's list and map; in Go, `List[T]` and `Map[K, V]`. A Python template used bare, such as `Selectable(...)`, can't check a value, so it raises a `TypeError` that names its copies and an application, such as `FormatsSelection` or `Selectable[FormatId, FormatId]`.
- **What a type checks.** Each type checks a JSON value as its schema does. A closed object rejects the members it doesn't name, and an open one keeps them. No member may be `null`. An integer written `1.0` is an integer, as JSON Schema compares numbers by value, and `true` isn't an integer term. A length counts code points. The formats follow their RFC grammars ([`src/sdk-formats.ts`](src/sdk-formats.ts)): `date-time` is RFC 3339, with a leap second only at 23:59 UTC, `duration` is RFC 3339 Appendix A, `uri` is RFC 3986, and `uuid` is the RFC 9562 string form, which every Ajv validator of the gates checks too in place of ajv-formats' looser one ([`src/formats.ts`](src/formats.ts)). Every runtime matches a pattern or a format against the whole string, so a trailing newline fails (type rules § 2). Go decodes into its types only after the value passes, with each optional member a pointer, or a list or map that `omitzero` leaves out, so a value encodes back to what it was decoded from.
- **Extension registry seam.** Each SDK has a registry that keys an extension's validator by the extension's URI, an absolute URI, and the digest of its definition, 64 lowercase hexadecimal characters, which it checks itself, since the model publishes no URI type: `ExtensionRegistry` in TypeScript, whose extension packages export `register(registry)`; in Python, with the entry-point group `openproposal.extensions`; and in Go, with `Extensions.Register` from an extension's `init`. The specification states no extension point, so the model declares none and no generated type calls the registry. The extension envelope it would serve is our proposal for the working group, not generated schema ([type rules § 12](docs/design/type-rules.md#12-proposed-not-in-the-specification)).
- **Vocabulary constants.** Each vocabulary with terms also has its terms as constants, named in the plural, for code built around enum members: `op.Channels.CTV == "ctv"` in Python, a class whose attributes are `Final`, so a type checker reads each as its literal, and `Channels.CTV` in TypeScript, a const object. A term is in upper snake case, such as `TransactionMechanisms.PREFERRED_DEAL`, and an integer term is `CODE_<n>`, such as `ApiFrameworks.CODE_6`, with its label as its doc comment. A field's type stays the vocabulary, so an open vocabulary's constants are its core terms, and a field of it still takes a namespaced term, or a vendor's code, as a plain value. Go already has a constant per term, such as `ChannelCTV`; its name capitalizes each word of the term, reads an upper-snake-case term as words, and writes an initialism in one case, as in `TransactionMechanismPreferredDeal` and `CredentialSchemeOAuth2ClientCredentials`.
- **Python wire helpers and the receive mode.** `op.parse(type_name, value, mode="strict")` checks a JSON value, as `json.loads` returns it, against a named type and returns the type's value, and `op.parse_json` does the same for a JSON text. The strict mode, the default, is the conformance check, which reaches the reference verdict. `mode="receive"` is an explicit opt-in for a receiver that must ignore what it doesn't know, as the agentic primitives' must-ignore rule asks: a closed object ignores the members it doesn't name, at any depth, as if they were absent, and everything else is checked as strictly. A model's own `model_validate` takes it as the validation context `{"openproposal_mode": "receive"}`. `op.dump(value)` and `op.dump_json(value)` write a value back with every absent member left out, never as `null`, since no type admits null, while an open object keeps its other members; a plain `model_dump()` writes each absent member as `null`, which the types reject. The tests run both modes on the 11 payloads the seller agent's own mapper writes from its router examples, in [`test/fixtures/seller-agent-payloads.json`](test/fixtures/seller-agent-payloads.json): the as-written trees accept 1 in the strict mode and 3 in the receive mode, and the trees with our proposals 0 and 1. Every type example parses, dumps, and parses again unchanged.
- **Provenance.** Each SDK states, as constants, which build it is: the specification's commit and the blob of its file, the lock, the variant (`as-written` or `proposed`), and the schema release the types match, as the digest of the build's schema tree that a release manifest records as its `digest`. In Python and TypeScript they are `SPEC_COMMIT`, `SPEC_BLOB`, `LOCK`, `VARIANT`, and `SCHEMA_RELEASE`; in Go, `SpecCommit`, `SpecBlob`, `Lock`, `Variant`, and `SchemaRelease`.
- **Gates.** On each lock, `npm run ci` checks:
  - the SDKs generate with no problem, and the names: each named type the schema emits is one declaration in each SDK, and no other type is;
  - drift: two runs of `npm run sdk` in separate processes write the in-process files, and the committed tree under `sdk/` holds exactly those files, byte for byte;
  - the TypeScript SDK typechecks under `tsc --strict`, and the Go SDK is `gofmt`-clean and passes `go vet`;
  - parity, gate 11: the TypeScript, Python, and Go types each reach the reference verdict on every case of the lock's committed corpus: each baseline, mutant, and trailing-newline mutant, and every rule payload, which the schema accepts; on every primitive's vectors, with a trailing-newline mutant of each valid one that has a spelling; and on every constructor's vectors, applied to their arguments through the generics, so a template no copy uses is held to its verdicts too. Each valid vector of an integer primitive is also sent as the JSON text `<v>.0` and `<v>e0`, which must pass, and `<v>.5`, which must fail, and each integer term of a vocabulary as `<t>.0`, so no serializer turns `1.0` into `1` before an SDK reads it. Each value a language accepts must encode back to the same JSON value. The Python leg runs [`tools/sdk/verdicts.py`](tools/sdk/verdicts.py) under the venv, which writes each accepted value back with the SDK's `dump` and fails where it differs from Pydantic's own `dump_python(mode="json", exclude_unset=True)`, with Pydantic as [`tools/sdk/requirements.txt`](tools/sdk/requirements.txt) hash-locks it; the Go leg builds a harness that names each case's type, since Go applies generics at compile time.

  Across the locks, every file git tracks under `sdk/` must be one that some lock generates.
- **Plain generator.** Type rules § 10 also asks that a plain generator, run on the published schema alone, write correct concrete classes, held to the same verdicts. [`src/plain-parity.ts`](src/plain-parity.ts) runs datamodel-code-generator 0.86.0, as [`tools/plaingen/requirements.txt`](tools/plaingen/requirements.txt) hash-locks it, with stock options only, on each committed schema file of a lock, one module per file, into `build/`. [`tools/plaingen/verdicts.py`](tools/plaingen/verdicts.py) then runs the parity cases whose type is concrete through the class of that name; a template application has no class there, since a plain generator has no generics, and the gate counts those cases. Each class must reach the reference verdict, raise nothing, and encode an accepted value back unchanged. Where the generator can't, such as with `if` / `then` and `minProperties`, which it drops, the divergence is a numbered exemption in [`plain-generator/exemptions.yaml`](specs/openproposal/plain-generator/exemptions.yaml) with the reason. The gate fails on a divergence no exemption lists, on a listed one that no longer occurs, and on a file written for another generator version.

## As-written variant

- **What it is.** The schemas with every change we propose switched off, so a reader can compare the specification as written with our proposals. [`variants/as-written.yaml`](specs/openproposal/variants/as-written.yaml) has one switch per decision record of kind `departure`. A switch names the record's option that the variant takes, which is never the chosen one, and says how the variant reads the fields the record changes. Every point the text leaves open stays filled by its gap record, in both builds.
- **What a switch does.** It changes the pipeline's inputs before the model resolves, with [`src/variant.ts`](src/variant.ts):
  - `replace`: a type the departure introduces is replaced everywhere by the form the text writes, such as `Uuid` by `Identifier`, any string (D-037), and each open vocabulary D-041 sets aside by `BareTerm`, a bare term.
  - `retype`: one element's type, or one member's, changes from the proposed form to the written one, such as a flight's start and end from `Timestamp` to `CalendarDate`, an RFC 3339 `full-date` (D-042). The switch states the proposed type, so a retype goes stale when the mapping changes.
  - `withhold`: the selectable template gives no `id` to an option whose members the text lists without one (D-047).
  - `convert`: a rule vector's value at a changed member becomes the written form, such as `true` to `1` (D-039), so every rule keeps its vectors.
  - `rewrite`: a description that states the proposed form says what the variant holds instead.
  - `findings`: the specification examples' failures the switch causes, each with why, such as the production options' `id`, which the audio example writes and the text doesn't list.

  The types the written forms need are the variant's `primitives`, in the kernel's format, with vectors: `Identifier`, `IntegerFlag` (`0` or `1`), `BareTerm`, and `CalendarDate`. Each switch, as written:

  | Departure | As written |
  |---|---|
  | D-037, minted IDs | Any string, as the text types `proposal_id` and `line_item_id` |
  | D-039, AdCOM flags | `placement.reward`, `instl`, and `skip` are `0` or `1` |
  | D-040, spans | `lead_time` is prose; `cadence`, `granularity`, and `attribution_window` are bare words such as `daily` and `30d`; `skipafter` and `min_interval_s` are whole seconds |
  | D-041, unlisted terms | Bare terms, such as `modeled` and `vast_4_2` |
  | D-042, flight dates | Calendar dates, such as `2026-10-06` |
  | D-047, option IDs | The production, measurement source, and reporting options have no `id`, so `included[]` and `pricing` can't name them |
- **Outputs.** `npm run emit`, `npm run rules`, `npm run type-examples`, and `npm run sdk` write each lock's as-written build beside the proposed one, under `as-written/` in each output directory, such as `schemas/as-written/with-open-prs/`, except the SDK types, where the as-written build is the default tree, `sdk/`, and ours is under `sdk/proposed/`. `--variant as-written` writes only the variant, and `--variant proposed` only ours. `npm run compare` writes [`comparison/as-written.md`](specs/openproposal/comparison/as-written.md), with its data in [`comparison/as-written.json`](specs/openproposal/comparison/as-written.json): each switch, each difference between the two builds on each lock, and the examples' failures in each build. The variant has no release manifest and no committed corpus.
- **Gates.** `npm run ci` checks:
  - the variant file: it is schema-valid; every departure has exactly one switch, with an option its record lists and doesn't choose; every replaced type is one the record introduces, a primitive that cites it or a type it sets aside; every retyped element is one the record covers; and the variant's primitives hold their vectors in Ajv, RE2, Python, and the reference oracle, with current sources;
  - the diff, on each lock: the variant's model differs from the proposed one only where a switch says, type by type and property by property;
  - fidelity, on each lock: the fidelity gate passes on the variant with no departure in force, so the variant states what the text states, in every form the oracle reads;
  - the outputs, on each lock: the schemas, rules, type examples, and SDK types, held to the gates the proposed ones are held to, with SDK parity on a corpus generated in process;
  - the examples, on each lock: every failure is a recorded gap finding, with the same kind and value, or a finding a switch lists, and every one of those still fails.

## AdCOM

AdCOM 1.0 is the registry of code lists that OpenRTB, OpenProposal, and the Deals API cite, such as `List: Device Types`. This phase generates its lists as a registry of JSON Schema vocabularies; its objects wait for a later phase. Its profile is [`specs/adcom/spec.yaml`](specs/adcom/spec.yaml), its plugin [`src/specs/adcom/`](src/specs/adcom/), and every path below is relative to [`specs/adcom/`](specs/adcom/).

- **Inputs.** [`spec-input/spec-lock.yaml`](specs/adcom/spec-input/spec-lock.yaml) pins `main` at `26c59ba`, the default, and [`spec-input/tag-202607.lock.yaml`](specs/adcom/spec-input/tag-202607.lock.yaml) the last tag, `AdCOM1.0-202607`, at `d67a6a8`, which a reachable clone must still tag there. The two differ only inside the `Content` object's table, so both give the same lists, code for code. AdCOM keeps no `examples/` folder.
- **Extraction.** AdCOM writes its tables in HTML, and [`src/html-table.ts`](src/html-table.ts) reads each into the table node the extractor reads a pipe table as, so a row's digest and quote are its source bytes. It reads a table as a browser shows it: a stray `</tr>` is skipped, a cell with no `<tr>` opens a row, and a cell's end closes its bold. Any tag a table doesn't use, any markup it can't read, and any unknown character reference fail extraction. Inline HTML in prose and headings, links, line breaks, code, bold, and italics, reads as markdown would write it. A section's ID is the anchor its heading writes, as `list_devicetypes`, and the body is the `SPECIFICATION` part. The text adopts no RFC 2119 convention and writes its keywords in either case, so a keyword in any case makes a statement (D-001). The IR holds 44 `List:` sections, 42 with a table of codes, and 46 objects' tables, with 411 attributes.
- **Lint.** [`src/specs/adcom/lint.ts`](src/specs/adcom/lint.ts) reports each heading anchor that departs from the `list_` and `object_` pattern, with how: a prefix, a spelling, or an abbreviation, or no anchor, and each `List:` section with no codes, `List: DOOH Venue Types (deprecated)` and `List: Placement Subtypes - Video` (D-014, D-015).
- **Mapping.** The `lists` module's rules ([`src/mapping-rules.ts`](src/mapping-rules.ts)) map each list with codes to one vocabulary, named by its title in PascalCase with its head noun in the singular, as `DeviceType` (D-002), each code labeled by its row, with a bold or plain name before a colon as the label's first part (D-018). A list that reserves codes for vendors, as `500+`, is open to them through the `VendorCode` primitive from its first code (D-008); `List: Start Delay Modes`'s `>0` row, every positive number of seconds, is the `MediaOffset` primitive, the vocabulary's extension (D-004). The `objects` module is deferred, citing D-003: its rule, `deferred-module`, maps each of its 639 rows and statements as informative, to no type yet, so the coverage gate still holds each to one entry.
- **Decision records.** [`decisions/`](specs/adcom/decisions/) holds 18 records, all gaps, none a departure, so AdCOM has one build per input and no variant with our proposals. Beyond how the text is read, they record AdCOM's known inconsistencies, each with the rows it quotes and feedback for the owners: lists "extended at any time" (D-007), the vendor range and the 51Degrees codes inside it (D-008, D-009), event types numbered one apart from OpenRTB Native 1.2 (D-010), VAST 4.4's missing creative subtype (D-011), timestamps and flags typed apart from the protocol buffer definitions (D-012, D-013), lists only OpenRTB 2.6 uses and the removed DOOH venue types (D-014), the removed placement subtypes (D-015), the revision the registry reads (D-016), deprecated category taxonomies (D-017), and how a code's label is read (D-018). The record-wording gate holds each record's question, chosen answer, and feedback to the owners' terms, as the feedback gates do for OpenProposal's.
- **Outputs.** Each lock's schemas, [`schemas/modules/lists/1/lists.json`](specs/adcom/schemas/modules/lists/1/lists.json) and the kernel's `VendorCode` and `MediaOffset`, with their `$id`s on the site's host under `/adcom/`; rules (none yet); the corpus; type examples; the release manifest; and the lock comparison, [`comparison/tag-202607.md`](specs/adcom/comparison/tag-202607.md). The kernel binding leaves out every kernel item AdCOM's lists don't use with `absent: true`.
- **Fidelity and round trip.** The oracle's readers ([`src/specs/adcom/fidelity-readers.ts`](src/specs/adcom/fidelity-readers.ts)) read each list from its rows alone: every code it names is valid, the vendor range's first two codes are valid and the code below it invalid, every positive number is valid where a `>0` row stands, and a code no row names, a code written as a string, and a fraction are invalid. The schemas give every one its verdict. The objects' rows are listed as unread. The round trip ([`src/specs/adcom/render.ts`](src/specs/adcom/render.ts)) renders each list's table back from its vocabulary, cell for cell, and its one difference, the `>0` row, is recorded under D-004 in [`roundtrip/differences.yaml`](specs/adcom/roundtrip/differences.yaml).
- **Enum drift report.** `npm run enum-drift` ([`src/enum-drift.ts`](src/enum-drift.ts)) compares each list, code by code, with the enum two other artifacts define for it: IAB Tech Lab's adcom-proto, `enums.proto` at `921f85e`, and Prebid's Go types, `adcom1/` at `0d01af1`. [`enum-drift/sources.yaml`](specs/adcom/enum-drift/sources.yaml), valid against [`enum-drift/sources.schema.json`](enum-drift/sources.schema.json), pins each artifact's folder by its git tree SHA and its license by blob; `enum-drift/snapshots/` holds the whole folder, unmodified, and the license, so the folder's hash proves no file is left out or changed, with no clone. It also pairs each list with each artifact's enum, or none, by meaning, since the names differ (adcom-proto's `LocationService` is List: IP Location Services). It writes [`enum-drift/enum-drift.md`](specs/adcom/enum-drift/enum-drift.md), with its data in `enum-drift/enum-drift.json`: the codes an enum lacks, the values it holds that no list or range does, its unset sentinel (a 0 named "unknown" where the list has no code 0), a Go integer type too narrow for a list's codes or vendor range, a code whose label and the enum's comment, or a protocol buffer value's name, state different versions, and an enum for a list whose table the text removed. Only codes and stated versions are compared; names differ by design. adcom-proto lacks 37 codes in 9 lists and has no enum for 6 lists; Prebid's types lack 29 codes in 7 lists, and its `FeedType`, an `int8`, can't hold a vendor's code from 500; adcom-proto's comment on Category Taxonomies' code 5 says 1.1 where the list says 2.1; and both still define the two lists whose tables AdCOM removed. The enum drift gates fail on a snapshot whose folder isn't its pinned tree, whose license isn't its pinned blob, or that holds another file; a reachable clone that disagrees; a list paired twice or not at all; an enum paired with no list or two; a line a reader can't read, or one that names an enum in a form it doesn't read; a report that two runs or the committed files don't match (enum-drift-deterministic, enum-drift-committed); and a tracked file under `enum-drift/` that is neither the sources file, a snapshot file, nor the report (enum-drift-tracked). AdCOM's landing page sums the report and links it.
- **Not yet.** The objects, their attributes, and the examples of Appendix C (D-003, D-006); SDK types; and the implementation feedback, whose records are drafted but not yet grouped into a report.

## Lock comparison

- **What it compares.** `npm run compare` runs the pipeline on every lock, from its committed IR and findings: the model, the schema files, the rules, the round trip, and the examples. For each lock other than the default, `spec-input/spec-lock.yaml`, it writes the comparison with the default lock: `comparison/<lock>.json`, canonical JSON with every list sorted, and `comparison/<lock>.md`, rendered from it. With the two locks there is one report, [`comparison/with-open-prs.md`](specs/openproposal/comparison/with-open-prs.md): how `main` plus the open PRs differs from `main`.
- **What it lists.**
  - Specification elements added, removed, or changed, by IR ID and digest, so a new field row is a new element.
  - Schema changes, from the release differ (see [Release](#release)) run as if the lock were the next release after the default lock: the models type by type, the rules by ID and content, and the schema files entry by entry, each `breaking`, `additive`, or `annotation`. A breaking change here is one the open PRs make to `main`, such as `geo`'s marker or a new required `Commitment` member.
  - Statements: where the model places each one, as a rule, an obligation, a statement a schema expresses, or an example, and the ones it places elsewhere.
  - Decisions the lock's model and rules cite and the default lock's don't, the reverse, and the ones both cite over an element that differs between the locks.
  - Findings: the spec lint's, the examples', and the round trip's, added, removed, or changed, each recorded finding with its decision and reason, and the conditions the schema leaves to the rules.
- **Gates.** `npm run ci` checks that the pipeline runs clean on every lock; that two runs of `npm run compare` in separate processes write the in-process bytes and the committed files equal them; and that every file git tracks under `comparison/` is one the comparison writes.

## Implementation feedback

- **What it is.** The decision records and the findings, grouped for the working group, as a follow-up on [IABTechLab/OpenProposal#121](https://github.com/IABTechLab/OpenProposal/issues/121), which proposed seven authoring rules for the specification. `npm run feedback` runs the pipeline on every lock, as `npm run compare` does, and writes three files to `feedback/` with [`src/feedback.ts`](src/feedback.ts): `feedback.json`, canonical JSON with every list sorted; `comment.md`, the comment to post on the issue; and `details.md`, the body of the gist the comment links. Both markdown files are functions of the JSON form, and the JSON form is a function of the records and of each lock's pipeline outputs.
- **The comment.** How many decisions the generation took: the points the text leaves open, and how many of them ask the specification to state something, by group, and apart from them the changes we propose to what the text or its examples settle, a decision record's `kind` (`gap` or `departure`); how many distinct places, by example and location, the specification's own examples fail on, split into those that only disagree with the text, those that only follow the text but not a change we propose, and those with one failure of each kind, so the three add up to the places; apart from them, the places where an example breaks a SHOULD rule, a warning, and those a rule can't decide; and the issue's lint findings counted by the authoring rule that removes them, on each lock.
- **The details.** The inputs, with each merged PR's head in merge order, and a summary of the open points, the example failures by cause, and the lint findings by authoring rule. Then every decision, numbered from 1 in reading order: the points the text leaves open, by group, each with what the specification should state (its `feedback`), what the schemas do until then (its chosen option), the sections and rows it rests on, the locks that cite it, and the examples that disagree on it; then the changes we propose, each with what we propose, what the schemas do, the rows it rests on, and the examples that follow the text but not the change. Then the example failures in two tables, one row per place, those that disagree with the text, with the side that should change, and those that follow the text but not a change we propose, each with the numbers of the decisions that cause it, the SHOULD rules' warnings, the checks the examples leave undecided, with what each turns on, every untagged union, one row each, with its forms on each lock and a summary's union in its projected form (type rules § 8 sends each one to the feedback, as a place for a tag), every condition the schema leaves to the rules, every round-trip difference, and every open lint finding with its sections and locks, and a permalink to at most four of its lines on `main`. A record writes a list as paragraphs that start with `- `, each after a blank line, which a folded YAML block keeps as line breaks; the details show each as an item under its label.
- **Groups.** A change we propose is listed apart. A point the text leaves open is grouped by the first stage of the pipeline that cites it: a kernel primitive (value formats), a constructor (selectable and settable fields), a mapping entry or declaration that types an element (types the tables leave open), a mapping entry that places a statement (where each statement is checked), or a rule's vectors (what each rule accepts). A lint finding's row follows from its kind: the seven authoring rules of #121, then the MUST statements that name no field, then the rest. A finding with a verdict in [`ir/exceptions.yaml`](specs/openproposal/ir/exceptions.yaml) is left out and counted. A superseded decision is left out; its successor is listed.
- **Working group's terms.** A decision's `feedback`, the reason of a recorded example finding or round-trip difference, and every line of `comment.md` and `details.md` below the generated header, can't cite this repository's documents or records, such as the type rules, a command, or a decision ID like `D-7`, because the working group doesn't have them. Nor can a line name a type of the model, read from each lock's model, in a code span or, for a name of two or more words such as `GeoBounds`, anywhere, unless the specification writes the name itself, in a Type cell or a code span, as it writes `Timestamp` and AdCOM's `Placement`: the text says what the type is instead, and an untagged union lists its forms in those words. The text names a decision by its number, as in "decision 4". The inputs name the PRs that we posted, listed in `OUR_PRS`.
- **A draft.** Each file opens with an HTML comment, hidden when rendered, that says it is generated and must be reviewed before posting. The comment links the gist as `<details-gist-url>`, to be replaced once the gist exists. Posting adds the disclosure line, as for every filing.
- **Gates.** `npm run ci` checks that the report builds from the same lock builds as the comparison and places every decision a lock cites, every open lint finding, every example failure, union, condition, and round-trip difference; that no feedback, reason, or line of the rendered text cites this repository; that no list item in a record folds into the line above; that each lint finding with a place on `main` links at least one of its lines, and every link opens the snapshot's specification at the full commit, at a non-blank line under the section it names; that two runs of `npm run feedback` in separate processes write the in-process bytes and the committed files equal them; and that every file git tracks under `feedback/` is one the report writes.

## CI

`npm run ci` runs [`scripts/ci.ts`](scripts/ci.ts), the one gate script. GitHub Actions runs the same script in [`.github/workflows/ci.yml`](.github/workflows/ci.yml), after `npm ci --ignore-scripts`, every `setup:*` script, and a fetch of `GATE_BASE`, the commit the gate decisions are compared with. Every gate runs for each spec on each of its locks, and a gate whose input failed to load fails too, so a green run has skipped nothing. A spec whose profile names no SDK packages, or no feedback target, as AdCOM's, has no SDK types or report to check, so those gates don't run on it; the optional-outputs gate fails where such a spec has the outputs they check: the default spec, which owns `sdk/`, with no SDK packages, or a spec with no feedback target whose `feedback/` git tracks. The script's header lists each gate. By gate:

The venv's Python is the version `setup:oracle` names, and each distribution a `tools/<tool>/requirements.txt` pins is installed at its pin, checked by [`tools/toolchain/installed.py`](tools/toolchain/installed.py). Beyond these 13, three gates check the gates:

- **Self-tests.** Every gate is defined under [`gates/`](gates/), listed in [`gates/index.ts`](gates/index.ts), with its check and at least one known-bad fixture: a mutation of the real input, such as the model with `currency` deleted from `Commitment`, a `Budget` twin of `Amount`, a property typed by the term grammar, or a schema that rejects a `units` commitment with no currency, which must stay valid. After the last gate, `npm run ci` reruns each gate on each fixture, and the gate must fail with the message the fixture expects. A fixture that needs files keeps them under `gates/data/<gate>/`. A gate with no fixture, or one that didn't run, fails the meta-check. Every finding of an independent review becomes a fixture or a vector before it is closed.
- **Fidelity.** See [Fidelity](#fidelity).
- **Guard.** A gate's fingerprint digests its definition and the functions its `code` names, each with every declaration it reaches, in its own file and, through the imports of repository modules, in any other, so a change to a helper such as `inScope` or `installFormats` changes it; its fixtures' data; the whole files and directories it names, such as `tsconfig.json` for the typecheck and `package.json` and `test/` for the test suite; and the exemptions it reads: `ir/exceptions.yaml`, `plain-generator/exemptions.yaml`, `roundtrip/differences.yaml`, `examples/findings.yaml`, `gates/fidelity-expected.yaml`, the shared structures of `kernel/domains.yaml`, the shared structures, homonyms, and money elements of each spec's kernel binding, and the decisions' `sets_aside`. The guard's own fingerprint also covers `scripts/ci.ts` and the harness. The guard fails when a fingerprint isn't the one the latest gate decision under [`gates/decisions/`](gates/decisions/) that names the gate accepts, so a gate can't be relaxed in the change that needs it relaxed to pass. `npm run gates` prints the changed gates as a record's `accepts` list. A concept a gate decision accepted leaves `kernel/domains.yaml` only through a later record's `retires`, so a gate that reports a concept unused can't remove it on its own, and a gate leaves only through a later record's `retires_gates`, so removing a gate never edits the record that accepted it. Gate decisions are append-only: the CI workflow sets `GATE_BASE` to the pull request's base, the push's previous commit, or the pushed commit when the push creates the branch, and fetches it, and `npm run ci` fails when `git diff -M --diff-filter=MDR` against it edits, deletes, or renames a record under `gates/decisions/`. Locally, `npm run ci` compares with `origin/main`, so fetch first. The guard's fixtures include the independent review's probes, each a fingerprint recomputed over the tree with one file changed: `inScope` always true, ajv-formats removed, `strict: false` in the corpus validators and in `tsconfig.json`, a test glob that matches nothing, and a deleted test file. The test suite also fails when fewer tests run than it holds (`MIN_TESTS` in [`gates/setup.ts`](gates/setup.ts)). A fingerprint is deterministic in CI, which a diff against the previous commit isn't in a shallow clone. Gate decisions are about the tooling and don't go to the working group.

The [lock comparison](#lock-comparison), the [implementation feedback](#implementation-feedback), and AdCOM's [enum drift report](#adcom), which compares its lists with other artifacts' enums (not the generated-output drift of gate 8), are gated with them: their reports are generated output, held to the committed bytes as gate 8 holds the others. The feedback is the forced-decisions log: every agent decision, rendered for the working group.

## Fidelity

The coverage gate proves that every IR element was placed somewhere. The fidelity gate proves that the schema still says what the element says. Its oracle, [`src/fidelity.ts`](src/fidelity.ts), with OpenProposal's readers in [`src/specs/openproposal/fidelity-readers.ts`](src/specs/openproposal/fidelity-readers.ts), reads the IR alone, never the mapping or the decisions, with one exception it holds to what can't widen a projection (below), and gets these forms:

| Form | Read from | Vectors |
|---|---|---|
| `required`, `optional` | A field description's leading REQUIRED or OPTIONAL sentence, a key table's Required cell (RECOMMENDED is optional), and the § 3.1 keys on every field the statement "Every field marked `selectable` MUST declare:" names | Present, valid; absent, invalid for a required member and valid for an optional one |
| `conditional` | REQUIRED when "`a = b`", "`a` is `b`", or "for <what> (`a` `b`, or …)", where `a` is a sibling or a member of an object the path runs through; or REQUIRED with members, "REQUIRED with either" naming the two members the sentence before names, each path from the member's own object, as `time_zone` with `daypart` or `frequency_cap.period` | Present while the condition holds, valid; absent, invalid; absent while `a` holds each other value its row lists, valid. A value the parenthesis qualifies with prose, as "video on `channel` `ctv`", is on neither side. For members: each path present, with the member valid and without it invalid; a path's first member present without the rest of it, and none present, without the member, valid |
| `type` | A field row's Type cell | The schema's value has the stated JSON type; `0.5` for a type that takes any number, valid; a value of another JSON type, a string of no format for a timestamp or an offset, and for a list a list of a wrong item, invalid |
| `values` | A value list in a table cell or an inline object, a sentence "`x` is `a` or `b`" (with "per <key>", each entry's value of a map), a named list's codes, "One value from List: … Label (n), …", and a sentence that gives members any code of named lists, with each list's codes from `kernel/lists.yaml`, the vendor codes a list reserves included, as List: API Frameworks reserves 500 and up | Each listed value, valid; an unlisted value, invalid, unless the text leaves the list open ("and other …", "such as …"); for a list with vendor codes, the first vendor code valid and the code below it invalid |
| `namespaced` | A row whose options are namespaced, "`available[]` of registry format ids namespaced by channel (`display/300x250`, …)"; a row that says "namespaced" any other way is listed as unread | Each example, valid; each example without its namespace, the part after its first `/`, such as `300x250`, invalid |
| `contains` | A MUST statement that a representation contains the paths the next block lists, and a block that continues it with "plus" | Each path present, valid; absent, invalid. Each object a listed path steps into, below the root, holds only the members the list's paths name there and a sibling the domain model makes one require, such as a rate's `currency`, so a projection widened back to its whole field fails |
| `optional`, for a list | A MUST statement that a representation gives "whichever of" the paths its own block lists the full record declares, as § 2.1's placement keys | Each step of each path present, valid; absent, valid. The list is a projection, as a `contains` list is |
| `member` | Each member an inline object in a row writes | The member present, valid |
| `empty` | "MAY be empty" in a key row | The empty list, valid |
| `example` | A YAML block the text writes under a field's name | Each member's value as the block writes it, valid, unless it holds a `<placeholder>` |

The one input the oracle takes from the mapping is a path a decision reads from an item a list writes in prose, as D-028 reads § 2.1's "property names" as `properties.available[].name`: the path joins that list's projection, so each object it steps into holds only what it names, and a step the schema doesn't hold fails. It states no presence, since the text names no member. A reading isn't only a check: each path it adds lets the objects it steps into hold one more member, so a reading of `formats.available[]` would let a summary carry the line item's whole `formats`. So a profile entry's `reads` names the prose item each path reads, and the oracle refuses, and the gate fails on, a reading of an item the list doesn't write in prose, of a list no MUST-contain statement introduces, or of a path that starts at a field one of the list's code paths names. The readings are part of the gate's fingerprint, as its exemptions are, so a new one needs a gate decision. The oracle finds a path's root by its rows' owner, the `proposal` or `line_item` document, or for a list as the type the model places the list in, and follows the path through the emitted schemas. It builds each vector from a valid baseline of the root, the corpus's builder (src/corpus.ts), and the emitted schema must give the vector its verdict. Every disagreement fails, unless a decision of kind `departure` covers that exact element and lists the constraint's form under that cover's `departs`, or [`gates/fidelity-expected.yaml`](gates/fidelity-expected.yaml) lists it. That file lists a disagreement under the open task that removes it, or, under `ruled`, as left to a rule because the schema can't state it, such as `plcmt` REQUIRED for a video line item, a condition on a member outside the `placement` object. A rule carries such a constraint only when it applies to an object on the constraint's path and one of its invalid vectors is a payload the constraint rules out; a rule that only names the element among its sources excuses nothing. A listed disagreement that no longer occurs fails too, and so does a form a departure's cover lists that excuses no disagreement. A `proposed` departure excuses, since none is accepted yet, and the gate's line names each departure with its status and count. The gate's line also reports the constraints by form, the statements it reads through a row (a row's presence restated, a MUST-contain statement read into its list), and every form the oracle can't read yet, with counts: prose conditions, prose value lists, prose items of a list, markers, an object no code span places, a key written as a placeholder, a type stated in prose, an example value with a placeholder, a closed vocabulary of the model that no closed value list the oracle reads reaches, the sentences about meaning, and the statements about behavior, which the rules and obligations carry.
