# Target rules

The JSON Schemas are what every other artifact is generated from. The specification, its IR, the mapping, and the decision records settle every question once, in the schemas the pipeline publishes. A **target** writes one more artifact from those published files alone: the documents a schema tree's `release.json` lists, as they are served at their `$id`s. A target never reads the IR, the model, the mapping, or the decisions. The rules below say what each target does that the schema doesn't say: the target's own policy. They apply to every spec. The [type rules](type-rules.md) decide what the schemas hold.

## 1. Every target

- **Input.** A target reads a published schema tree (`src/targets/schema-tree.ts`): the documents its `release.json` lists, each with its `$id`. Another lock's tree nested under it has a manifest of its own and isn't read. A spec's profile may give a target a setting, such as a package name, under `names`; the target has no default for it. **Gate:** every module the emitter reaches is under `src/targets/` and is imported by its path, never by a computed name; only the tree's reader imports `node:fs`, and the others import `node:path` at most, no package; and the target's code with a copy of the tracked `schemas/`, alone in a folder outside the repository, writes the spec's bytes.
- **Generic code.** A target's code names no spec: every name it writes comes from a schema or a profile. **Gate:** no file under `src/targets/`, nor a target's CLI, names a spec's folder or the name its profile gives, in any case.
- **Names of codes.** An integer-coded vocabulary's codes are named by the rule in [type rules § 6](type-rules.md#6-vocabularies), "Code names" (`src/targets/names.ts`): the UPPER_SNAKE of each code's `title`, `CODE_` before a leading digit, cut at its last underscore before 48 characters, and the code as a suffix where two names collide, a negative code written `MINUS_`. A title with no ASCII letter or digit gives `CODE_<code>`. A title that gives an awkward name is fixed in the schema's title, through the specification or its mapping, never in the target.
- **Output.** A target's files are committed under its folder in the spec's folder (`src/targets/layout.ts`), written whole by each run, and held to two things: two runs give the same bytes, and the committed files equal a fresh run. They are unofficial: no specification's owner publishes them.

## 2. Protocol buffers

`npm run proto` (`src/targets/proto.ts`) writes each integer-coded vocabulary, a `type: integer` schema whose `oneOf` has `const` branches, as a proto3 enum. It writes enums only; messages wait for the specs' objects.

- **Package.** One per spec: the profile's `names.proto.package`, lowercase dotted words ending in a version, such as AdCOM's `com.postindustria.ads.adcom.v1`: the publisher's namespace, `com.postindustria.ads`, which holds IAB and other specifications alike, then the spec's folder name without its hyphens, then the version. The file's folders are the package's, as `com/postindustria/ads/adcom/v1/`. **Gate:** the spec-profile gate fails a package whose segment before the version isn't the spec's folder name without its hyphens. A spec whose profile names none has no proto files.
- **Files.** One `.proto` file for each schema document that defines a vocabulary, named as the document in lower_snake_case, under the package's folders, since a proto file's folders are its package: `modules/lists/1/lists.json` gives `<package as folders>/lists.proto`, under the spec's `proto/`, and `buyer-seat.json` gives `buyer_seat.proto`. Two documents of one name fail; the SDK emitters' module per document path (the schema tree's folders) is for a language whose modules aren't its packages.
- **Enums.** One for each vocabulary, named as its `$defs` key. The comment gives the vocabulary's title and description and the schema node it comes from, as `<$id>#/$defs/<name>`.
- **Values.** One for each code, numbered as the code, so a field reads the same number as any other artifact that has the code. A value's name is the enum's name in UPPER_SNAKE, a word at each capital, then `_` and the code's name: `ApiFramework`'s code 6, "MRAID 3.0", is `API_FRAMEWORK_MRAID_3_0`. Proto scopes a value's name in its enum's package, not in its enum, so the prefix keeps the names of two enums apart; a name two enums or two values of a package still share fails. The comment gives the code's title and its description.
- **Zero.** Where the vocabulary has no code 0, the first value is `<ENUM>_UNSPECIFIED = 0`, as Google's proto style guide names the zero value: no code, the value an unset field holds. A code whose name is `UNSPECIFIED` then takes its code as a suffix. Where the vocabulary has a code 0, that code is the first value, under its own name: the specification defines 0 as a code, and a value's number is its code, so the spec's choice stands over the style guide's form, and over `buf lint`'s `ENUM_ZERO_VALUE_SUFFIX`, which would rather a zero that means nothing.
- **Branches that aren't one code.** A vendor range, such as `{ type: integer, minimum: 500 }`, and any other extension, such as a media offset of `type: integer` with `not` a code, are no values. A proto3 enum is open, so a field of the enum keeps such a number, within int32. The enum's comment says what each such branch allows. A schema that is titled codes but no list, such as a two-valued flag of `0` and `1`, reads the same way and is an enum too: the schema alone doesn't say it is a flag.
- **Layout of the text.** Comments wrap at 80 columns, the style guide's limit; a word longer than that, such as a URL, and each enum's source, `From <$id>#/$defs/<name>`, stand on a line of their own. A value's line isn't wrapped, so a long name runs past 80.
- **What fails.** A vocabulary or a branch with a keyword the target doesn't read, a code that isn't an integer or lies outside int32, a code listed twice, a code's branch with no title, and a `$defs` key that isn't PascalCase.
- **Compiler.** **Gate:** the protoc that `grpcio-tools`, pinned in `tools/proto/requirements.txt` and installed by `npm run setup:proto`, bundles compiles every file, so every machine and CI run one protoc.
- **Names and compatibility.** Every name follows the specification, through the schema: the enum's from the vocabulary, the value's from the code's title, prefixed as proto scoping requires. No name comes from another artifact, and there is no table of names to keep: an awkward name is fixed in the title (type rules § 6). Compatibility with other artifacts is binary only: a value's number is its code, so a field carries the same number in any artifact that has the code.
- **JSON on the wire.** A service on the generated proto and a client on the schemas must exchange the same JSON: what the schema validates is what the proto's JSON mapping writes and reads (not built yet). The rules, for every spec once the target writes messages:
  - A field's proto name is the schema's property name, and its `json_name` is set to the same, so protoc's camelCase never renames a key.
  - Every scalar and enum field that isn't repeated is proto3 `optional`, so an absent member stays absent rather than reading as its zero.
  - An integer field is `int32` where the schema's range fits in it, and else `int64`.
  - A titled two-valued flag, such as the kernel's `IntegerFlag`, is an integer enum like any titled codes, never `bool`, since the JSON holds `0` or `1`.
  - An extension object, `ext`, is `google.protobuf.Struct`.
  - Enum values travel as their numbers, and `int64` as JSON numbers, not strings, through a connect codec the Go output ships. Today's files hold enums only, so the one rule that applies is that an enum value travels as its number: write them with that codec, or with protojson's `MarshalOptions` and `UseEnumNumbers`, since the specs' JSON writes integers; protojson reads a number or a name either way.
- **Field numbers.** A message's field numbers are the wire's names, so they are fixed once and kept, by the owner's decision (not built yet; the numbering file and its gate arrive with the first messages, and AdCOM's file holds enums only today):
  - For a message adcom-proto defines, each field takes adcom-proto's field number, paired by the specification's field name, read from adcom-proto at `921f85e`, the commit the enum drift report pins. Today's snapshot holds only its enums folder, whose one message wraps enums; the message files join the snapshot, pinned by their tree as the enums folder is, with the first messages. Only the numbers are taken: no name, type, package, or option. This is the one place another artifact seeds the output, and it seeds the numbering file, not the emitter, which reads that file beside the schemas.
  - Every other field, and every field of a message adcom-proto lacks, takes the next free number, in the specification's row order.
  - The numbers live in a committed numbering file per spec and message, which only grows: a number is never renumbered or reused, and a field the specification removes becomes `reserved`, by its number and its name.
  - **Gate:** `buf breaking` against the previous release's proto, with known-bad fixtures: a renumbered field, a reused number, a removed field that isn't reserved, and a seeded field whose number isn't adcom-proto's.
  - An enum value's number stays its code.
- **Against other artifacts.** For a registry with an enum drift report, the report compares the proto files with the registry, list by list, and a gate holds them to it: an enum for every list with codes, every code at its number, and no other value but the unset one, a number in a vendor range or a positive-number row included, since such a range is no value. The report then lists, for a reader, each enum and value that another artifact names otherwise.
